# CartCare 重点代码

本文档按**请求链路**重组，目标不是把文件逐个罗列，而是回答一个问题：

> 用户发来一条消息后，CartCare 的核心代码如何把“识别、路由、工具、生成、记忆、监控、评测”连接起来？

如果你是第一次看这个项目，建议按下面顺序读：

1. /chat 主链路
2. core/intent_recognizer.py
3. agents/agent_orchestrator.py
4. agents/tools.py、mcp/tool_manager.py 和 mcp/knowledge_base.py
5. providers/ 动态业务 Provider 层
6. memory/conversation_memory.py
7. core/skill_loader.py
8. monitor/performance_monitor.py
9. evaluation/evaluator.py

---

## 1. /chat 主链路

**文件**：api/main.py

当前代码的实际顺序是：

~~~text
读取记忆
  -> 意图识别
  -> 构造带 intent / entities / urgency / history 的 Request
  -> Orchestrator 生成路由决策
  -> Agent 调用 LLM；模型需要时按白名单执行工具（最多 3 轮）
       -> search_knowledge_base（按需触发 RAG）
  -> 写回用户和助手消息
  -> 异步更新用户画像
~~~

关键代码的等价结构如下：

~~~python
mem_ctx = await _memory.get_context(req.user_id, conv_id, query=req.message)
history = [
    {"role": m.role.value, "content": m.content}
    for m in mem_ctx.recent_messages[-5:]
] if mem_ctx.recent_messages else None

intent_result = await _orchestrator.recognize_intent(
    req.message,
    history=history,
)
orch_req = Request(
    message=req.message,
    user_id=req.user_id,
    conv_id=conv_id,
    context=mem_ctx.to_prompt_text(),
    history=history,
    entities=intent_result.entities,
    intent=intent_result.intent,
    intent_group=intent_result.intent_group,
    urgency=intent_result.urgency,
    intent_confidence=intent_result.confidence,
)
result = await _orchestrator.run(orch_req)
await _memory.add_message(req.user_id, conv_id, MsgRole.USER, req.message)
await _memory.add_message(req.user_id, conv_id, MsgRole.ASSISTANT, result.response)
asyncio.create_task(_memory.update_profile(req.user_id, conv_id))
~~~

这里需要特别区分：

- api/main.py 仍保留 _build_knowledge_context 辅助函数，但当前 /chat 没有调用它；真实 RAG 执行路径是 Agent 通过 search_knowledge_base 工具按需调用。
- Orchestrator.run() 会生成 RoutingDecision，选择 General、Technical、Billing 或 Escalation Agent；复合问题可能并行执行主 Agent 和辅助 Agent。
- Agent 工具调用有角色白名单、参数校验和最多 3 轮的 tool loop。
- ChatResponse 的 knowledge_used 只有在实际工具名 search_knowledge_base 出现在 tools_used 时才为 true。
- Monitor 在后台采集统计；Eval 通过独立的 /eval/run 端点启动，不是每个 /chat 请求的同步步骤。
- `providers/` 当前提供动态业务事实的只读合约；`agents/tools.py` 的 `build_business_tools()` 将其接入 Agent Tools，API lifespan 负责注入测试/演示 backend，因此 `/chat` 可以查询这些动态事实，但仍未接入真实外部电商系统。

## 2. 三路融合意图识别

**文件**：`core/intent_recognizer.py`

这是 CartCare 的第一个核心层：先把“用户到底想干什么”结构化出来。

### 识别链路

```text
LLM Few-shot
Embedding 相似度
Pattern 规则匹配
-> 加权投票
-> intent / intent_group / confidence / source_scores / urgency / entities
```

### 代码层设计

`recognize()` 会并行启动 LLM 和 Embedding，Pattern 同步执行：

```python
llm_task = asyncio.create_task(self._llm_recognize(message, history))
emb_task = asyncio.create_task(self._embedding_recognize(message)) if self._embedding_enabled else None
pat = self._pattern_recognize(message)
```

然后在 `_vote()` 里做融合：

- LLM 负责语义理解
- Embedding 负责和模板样本做相似度匹配
- Pattern 负责快速兜底和细粒度纠偏

### 输出字段

`IntentResult` 里真正有用的不是只有 `intent`，还有：

- `intent_group`
- `confidence`
- `source_scores`
- `urgency`
- `entities`

其中 `entities` 会规则抽取：

- `order_id`
- `date`
- `amount`
- `error_code`

### 紧急度

系统把紧急度分成 4 级：

- `LOW`
- `MEDIUM`
- `HIGH`
- `CRITICAL`

规则来自两类信号：

- 消息中的紧急关键词
- 意图本身是否属于转人工、投诉等高风险场景

### 面试时怎么讲

> 我把意图识别做成了三路融合，不是单一分类器。LLM 负责语义，Embedding 负责相似度，Pattern 负责兜底，最后输出 intent、intent_group、source_scores、urgency 和 entities，直接给后续路由使用。

## 3. MCP 工具层

**文件**：`mcp/tool_manager.py`

工具层负责两件事：

1. 把检索/外部能力标准化
2. 让调用具备缓存、超时、熔断和 fallback

### 关键机制

```text
参数校验 -> 缓存 -> 熔断检查 -> 超时控制 -> 失败降级 -> 统计回写
```

### 为什么重要

如果没有这一层，RAG 和外部工具调用会直接拖垮主链路稳定性。

### 重点设计

- `asyncio.wait_for()` 控制超时
- JSON Schema 校验参数
- 连续失败后触发熔断
- fallback 结果要可解释
- 每次调用会更新成功率和延迟统计，供 Monitor 使用

### 面试时怎么讲

> 我没有把外部能力直接塞给 Agent，而是先抽象成工具层，再加缓存、熔断和 fallback。这样工具失败时系统能降级，而不是整条链路一起挂掉。

## 4. 知识库与 RAG

**文件**：agents/tools.py、mcp/tool_manager.py、mcp/knowledge_base.py

当前 /chat 的 RAG 执行路径是 Agent tool loop 内的共享工具：

~~~text
Agent 获得 search_knowledge_base 和只读业务 Provider Tools 白名单
  -> 模型按需发出 tool_use
  -> build_shared_rag_tools() 调用 MCPToolManager.search_with_rewrite()
  -> 查询改写
  -> 子查询并行召回 knowledge_search
  -> 合并去重
  -> 可选 LLM 重排
  -> tool_result 回填给 Agent
  -> Agent 继续生成回复
~~~

/search 端点则直接调用 MCPToolManager.search_with_rewrite()，适合单独调试查询改写、召回、去重、重排和 Top-K。mcp/ 是项目自研的本地工具层，不代表已经接入标准 Model Context Protocol SDK 或 transport。

### 为什么需要按需调用

- 问候、反馈、转人工等请求通常不需要知识库。
- 业务问题可以让 Agent 根据上下文和角色规范决定是否检索。
- 即使是业务类请求，模型没有发出 tool_use 时，/chat 也不会把 RAG 结果强行塞进上下文。

工具层还负责参数校验、缓存、超时、熔断、fallback 和运行统计。动态订单、物流、库存、支付、退款事实不应通过这个知识库工具伪造。

## 5. 动态业务 Provider 层

**目录**：`providers/`

Provider 层负责提供动态业务事实的统一 source of truth，但不负责 Agent 决策、退款资格判断或写操作。

```text
Provider
  -> BusinessBackend Protocol
  -> Product / Order / Inventory / Logistics / Refund 领域模型
  -> 结构化结果或 typed provider error
```

当前实现包括：

- `models.py`：Pydantic 结构化模型和状态枚举
- `errors.py`：`not_found`、`unauthorized`、`dependency_failure`、`invalid_data`
- `interfaces.py`：与具体 DB/API 解耦的 `BusinessBackend` Protocol
- `implementations.py`：五类只读 Provider
- `mock_backend.py`：明确标记为测试/演示用途的 JSON fixture 内存 Backend

`tests/fixtures/business_provider_data.json` 和 `providers/fixtures/business_provider_data.json` 都是测试/演示数据，不代表已接入真实电商系统。`agents/tools.py` 的 `build_business_tools()` 将 Provider 注入为只读 Agent Tools；工具 handler 不直接读取 fixture。T04 负责确定性 Policy Result，T05 负责审批/幂等执行。

`policies/engine.py` 的 `PolicyEngine` 只消费 Provider 返回的 `Order` / `RefundRecord` 模型及显式客户标识、时间和金额；`policies/models.py` 定义稳定的 `PolicyDecision`。它对退款窗口、订单状态、所有权、金额阈值和审批条件给出确定性结果，不查询数据源，也不执行写操作。当前 `/chat` 的只读工具不会自动调用 Policy Engine；T05 才负责 pending action、审批和执行控制。

## 6. 多 Agent 编排

**文件**：`agents/agent_orchestrator.py`

这是 CartCare 的第二个核心层：先决定“谁来处理”，再决定“怎么协作”。

### 不是 prompt-only

当前架构已经不是简单的：

```text
一个编排器 + 几个 prompt 不同的 Agent
```

而是：

```text
意图识别 -> 路由决策 -> 主 Agent / 辅助 Agent / 升级 Agent
          -> 单 Agent 执行或并行协作
          -> ResponseComposer 合并结果
```

### Agent 角色

- `GeneralAgent`
- `TechnicalAgent`
- `BillingAgent`
- `EscalationAgent`

### 为什么 `pool` 是 `list`

`_pool: Dict[AgentType, List[BaseAgent]]` 的设计，是为了支持：

- 同角色多实例
- 不同模型配置
- 在线表现差异化路由
- 灰度和降级

当前默认每类只有一个实例，但结构已经预留扩展。

### 路由依据

路由时会综合：

- `intent`
- `urgency`
- `entities`
- 关键词
- 在线表现

复杂请求会生成：

- `primary_agent`
- `supporting_agents`

比如“登录报错 401，而且这个月还重复扣款了”，可能会同时路由给技术和账单。

### Agent 执行时的工具边界

每个 Agent 都有自己的 `AgentProfile`，里面定义了：

- 职责
- 工作流
- 输入契约
- 输出契约
- 升级条件
- `tool_scope`

这说明多 Agent 的差异不只是 prompt，而是角色契约、工具边界和路由位置都不同。

### 面试时怎么讲

> CartCare 的多 Agent 不是 prompt-only，而是路由驱动的角色编排。每个 Agent 都有自己的契约和工具边界，复杂问题还能主辅协作并行处理，在线表现还会反馈到下一轮路由里。

## 7. 共享工具与 Skills

**文件**：`agents/agent_orchestrator.py`、`core/skill_loader.py`

这一层解决的是“Agent 怎么说、怎么做、边界在哪”。

### 工具白名单

Agent 调用工具时不是直接裸调，而是：

- 先拿白名单
- 再做参数校验
- 再执行 handler
- 最后把结果回填给模型

### Skills 注入

`_build_system_prompt()` 会把动态 Skills 拼进 system prompt：

```python
skill_prompt = self._skill_manager.prompt_for(req.message, self.agent_type.value)
```

这意味着 Skills 是在**选定 Agent 之后**生效的，不影响路由，只影响执行策略。

### 为什么这样拆

- 知识库回答“事实是什么”
- Skills 规定“应该怎么处理”

所以它们不是一回事。

### 热更新

修改 `skills/*/SKILL.md` 后可以通过 `/skills/reload` 重新加载，不用重启服务。

## 8. 三层记忆

**文件**：`memory/conversation_memory.py`

CartCare 把记忆拆成三层：

- **工作记忆**：Redis，保存当前会话最近消息
- **情景记忆**：ChromaDB `episodic`，保存压缩摘要
- **用户画像**：ChromaDB `user_profile`，保存长期偏好

### 这样拆的原因

- 当前轮要短
- 跨轮信息要保留
- 长期偏好不能丢

### 关键实现

- 工作记忆超过阈值会自动压缩
- 压缩不是简单拼接，而是合并摘要
- `to_prompt_text()` 只拼少量最近消息，避免上下文过长
- `update_profile()` 异步执行，不阻塞接口响应

### 面试时怎么讲

> 我把记忆拆成工作记忆、情景记忆和用户画像三层，分别对应当前轮、跨轮线索和长期偏好。这样能控制上下文长度，也能保留跨会话连续性。

## 9. Monitor 在线观测

**文件**：`monitor/performance_monitor.py`

Monitor 的作用不是“看板”，而是把运行情况重新送回路由层。

### 它做什么

- 周期性读取 Agent 和工具统计
- 检测成功率和延迟异常
- 生成建议
- 写回 `monitor_penalty`

### 和路由的关系

`AgentStats.routing_score()` 会把 `monitor_penalty` 算进去。  
所以在线表现差的 Agent，后续会被自动降低选中概率。

### 这个闭环很重要

这说明系统不是静态路由，而是会根据线上质量自动调整。

### 面试时怎么讲

> 我把监控结果接回了路由层，而不是只做展示。Agent 的成功率和延迟会影响 routing_score，这样系统能根据在线表现自动避开状态变差的节点。

## 10. 端到端评测

**文件**：`evaluation/evaluator.py`

评测层解决的是“怎么知道系统有没有变好”。

### 两类评测

1. **意图识别评测**
   - Accuracy
   - Macro-F1
   - 单类 Precision / Recall / F1

2. **对话质量评测**
   - 用 LLM-as-Judge 打分
   - 维度是 relevance、accuracy、completeness、helpfulness

### 为什么不是 mock

评测会真实调用 `AgentOrchestrator.run()` 生成回复，再交给 judge 评分。  
这意味着它测的是真实链路，不是伪造输出。

### 回归检测

评测结果可以和历史基线对比，用来判断有没有退化。

### 面试时怎么讲

> 我不只做了多 Agent 编排，还把意图识别和回复质量都接进了评测闭环。这样系统不是靠感觉调，而是能用 Accuracy、Macro-F1 和 LLM-as-Judge 持续回归。

## 11. 这篇文档该怎么读

如果你是准备面试，我建议按这个顺序背：

1. `/chat` 主链路
2. 三路融合意图识别
3. 多 Agent 路由
4. 工具白名单和 Skills
5. 三层记忆
6. Monitor 闭环
7. 评测闭环

如果要一句话总结这套代码：

> CartCare 不是一个简单聊天机器人，而是一个把“识别、路由、检索、执行、记忆、监控、评测”串成闭环的多 Agent 客服运行时。
