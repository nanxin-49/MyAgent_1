# CartCare 重点代码

## 可执行生产请求路径

api/main.py 的 lifespan 创建 agents/support_agent.py 的 SupportRuntime，注入原有 RAG 和业务工具。/chat 读取 Memory、构建 Request、调用 runtime.run、回写 Memory，再返回响应和引用；不调用 recognize_intent、specialist routing 或 Composer。

N05 在 runtime.run 后增加 `_observed_action_results`：从本请求危险工具 Trace 取动作编号，通过 ActionService.get 的 Principal/owner gate 读取并复制既有回执。响应追加 action_results、memory_write_status、warning_codes；至少一个动作确认 completed 且有执行回执时，后续 Memory 写入失败返回真实动作状态与固定降级码，其余写入异常仍传播。HTTP 成功不能替代逐动作状态判断。未改 Agent Loop、Policy/HITL、N01 绑定或 MemoryManager；实现边界和测试见 `tests/test_action_memory_consistency.py`。

SupportRuntime 每请求创建独立 SingleSupportAgent，复用 agents/agent_orchestrator.py 的 BaseAgent 和 Request / AgentProfile 类型。统一注册表合并原有 helper tools 与共享工具。沿用 T10 Single 的基础职责、skills 与 generation 0.2 / 1200；A02追加 request_handoff 和交接状态/措辞约束，不再宣称提示词完全相等。不会以 case 标签引导生产行为。请求独立 Agent 状态避免并发污染 _last_tools。

A02：`SingleSupportAgent.handle` 对当前明确人工请求直接经 `execute_tool(request_handoff)` 申请；其余由Agent选工具。`agents/tools.py:build_handoff_tools` → `core/handoff.py:HandoffService.request` 再校验Principal/策略，按subject/owner/conv/key与消息hash幂等，创建固定安全摘要的进程内模拟记录。`SupportResult.handoff`、Trace根节点handoff和每次工具handoff_result保留真实事实，API追加同形HandoffResult；`escalated=handoff_created`。后续模型失败/拒绝不覆盖已创建回执，最终交接回复由后端渲染，N05写失败保留原则也覆盖已创建交接。`GET /handoffs/{id}`仅owner可读；摘要helper不建单。独立结构化评分见 `evaluation/handoff_eval.py`，细节及限制见 `tests/test_handoff.py`。

```text
Memory / context → SupportRuntime.run → SingleSupportAgent.handle
→ BaseAgent._call_llm（默认最多 3 轮 / 8 步，停止原因见下）
→ agents/tools.py → core/tool_contract.py → guarded handlers
→ Response / Trace / Memory 回写
```

## 统一工具和确定性业务层

core/auth.py 的 AuthAdapter 在HTTP入口验证Principal；api/main.py校验body身份声明，将Principal与服务端customer_id传入Request。agents/tools.py的build_business_tools提供get_product、get_order、get_shipment、check_inventory、get_refund_status；工具先检查Principal与Request.user_id一致，Provider再检查ownership。ActionService公开方法独立拒绝缺失Principal或无权主体；approve要求范围内的独立reviewer，记录requested_by/reviewed_by并保留owner。Trace/管理依赖require_admin，Demo需显式回环认证，默认拒绝。API和配置细节见README及ADR，不接受模型/客户端覆盖身份。

build_action_tools 的 request_refund / request_cancel_order 仅请求 ActionService。actions/ 保留 PendingAction、状态机、审批/拒绝/恢复、执行器和幂等 Store；policies/ 保留基于 Provider 事实的确定性资格、金额和风险规则。/actions/{id}/approve、reject、resume 的 API 未改。危险工具不通过 Tool Runtime 自动重试或绕过审批。

N04：lifespan 创建 InMemoryBusinessBackend 后，将其 state 传入 InMemoryBusinessActionBackend，读写使用同一业务表与锁。execute_refund 先校验 pending RefundRecord，再在锁内写记录和 refund_pending 订单状态；捕获提交异常时回滚。Action completed 只表示模拟命令完成，Refund pending 表示申请待处理，回执附 refund_id/refund_status。get_refund_status → RefundProvider → get_refund_for_order 读取最新 updated_at 的申请，旧记录仍保留；Policy 将 pending 视为已有活跃退款。写后读验收见 `tests/test_refund_read_write_consistency.py`。

core/tool_contract.py 提供严格 schema、风险/超时/重试元数据、typed result、错误和审计 trace。所有工具对 Single 可见不等于获得直接写后端能力。

H3-1：`core/stop_reason.py` 的 `StopReason` 记录每次 turn 的停止原因（completed / needs_clarification / awaiting_approval / budget_exhausted / unrecoverable_error / loop_detected），写入 SupportResult 和 Trace 根节点，可从 `/trace/tool/{request_id}` 读取；needs_clarification 是窄措辞观测，不参与路由或回复改写。`HarnessConfig` 增加 max_tool_steps=8、max_tokens_per_turn=60000、duplicate_call_limit=3、tool_timeout_s=30；步数、token 和重复调用限制只在 loop_control 开启时生效。`execute_tool(timeout_s=...)` 对只读工具取契约与 harness 的较小值；写动作仍不设执行超时，N11 留给 H4-3。

H3-2：失败工具结果统一补齐 `error_code`、`error_type`、`retryable`、`suggested_action`（映射在 `core/tool_contract.py`，只是给模型的建议，不改变 Policy/执行）；模型可见 tool_result 超过 `HarnessConfig.max_tool_result_chars=8000` 时截断并标 `truncated`，Trace 仍从完整 payload 提取字段。`error_feedback=False` 仍在截断后覆盖为 ack。`evaluation/h3_2/` 用确定性恢复探针比较开/关（on 5/5、off 0/5），真实模型恢复率留给 H3-6。

H3-3：`core/context_budget.py` 用估算 token（ASCII/4 + 非 ASCII 字符）统计每轮上下文构成（system、工具 schema、Memory、当前用户消息、对话、工具结果、检索片段），写入 `SupportResult.context_rounds` 和 Trace 根节点。每轮请求前若超过 `HarnessConfig.max_context_tokens=16000` 且 `context_compression` 开启，按“旧工具结果 → 背景消息 → 较早对话”压缩；system、工具 schema、当前用户消息不动，仍有剩余时标 `over_budget`。确定性两臂对比见 `evaluation/h3_3/`（成功 1.0/1.0，估算 token 59,953 vs 170,170）。

H3-4：`core/output_consistency.py` 检查回答中的退款/取消完成声明与“已到账”声明，`SingleSupportAgent.handle` 在 `output_consistency` 开启时把它们与本轮 `action_result` / 交接回执比对；不一致则改写为动作回执或固定如实话术，并把 `consistency_warnings`（code/kind/claimed/observed/blocking）写入 `SupportResult` 和 Trace 根节点。交接声明沿用既有 `_claims_completed_handoff` 守卫。`output_consistency=False` 仅用于评测消融。历史回放见 `tests/test_h3_4_output_consistency.py`。

H3-5：`core/step_trace.py` 的 `summarize_parameters` / `summarize_tool_trace` / `new_model_step` 生成有界摘要。`BaseAgent._call_llm` 每轮模型调用追加一个 step（`input_tokens`、`output_tokens`、`latency_ms`、`tools`、`stop_reason`），工具执行或跳过后把工具名、参数摘要、结果摘要和 `aux_model_calls` 归入该 step；token 预算、重复调用、步数预算、完成和异常都会写该步停止原因。`SupportResult.steps` 与 Trace 根节点的 `steps`/`step_count`/`step_scope` 可从 `/trace/tool/{request_id}` 复盘；`step` 与 `context_rounds[].round` 对齐。不保存 prompt、模型文本、隐藏推理和原始 Memory 内容；确定性交接路径没有模型步，交接工具仍在 `tool_calls`。测试见 `tests/test_h3_5_step_observability.py`。

H3-6：`evaluation/h3_6/cases.json` 保存 24 条复合售后用例（每条 2–3 个 `demands`，覆盖独立写动作、依赖、越权、故障恢复、重复诱导、部分成功/交接）；`evaluation/h3_6/composite.py` 的 `evaluate_demands` 按 `tool_traces` 逐诉求匹配 action/read/rag/handoff，输出 `completed`/`awaiting_approval`/`rejected`/`failed`/`answered`/`no_answer`/`not_called`，并检查额外写、重复写、每个写动作独立 Policy 回执、整体完成状态、回答一致性和故障恢复。`run_composite.py` 是确定性 runner；`run_ablation.py` 用 `evaluation/h2_4/profile.py` 的 6 个 profile（full、bare、no_guardrails、no_error_feedback、no_context_compression、no_loop_control）调用真实模型 runner，每臂独立 ledger/预算。`evaluation/h2_3/real_model.py` 的 `score_case` 在有 `demands` 时走复合评分，并支持 case 级 `faults`；H2-3 180 条行为不变。C03：`BaseAgent._last_action_receipt` 枚举本轮全部 action（按 action_id 去重，reused 标注），单 action 文本保持不变，多 action 输出逐项回执，避免末轮只报最近一个动作。测试见 `tests/test_h3_6_composite.py`、`tests/test_h3_6_ablation.py`。

H2-5：`evaluation/h2_5/` 用 conda 环境预计算 `bge-small-zh-v1.5` 向量（固定 revision/权重 SHA、CLS pooling、L2、query prefix），项目 `.venv` 用 `LookupEmbedding` 只读 patch `mcp.knowledge_base` 的 embedding seam，在独立 Chroma collection 上比较 B0-calibrated（0.20）、semantic（dev 锁定 0.65）、hybrid（semantic 阈值门 + 字符 bigram BM25/RRF）。评分复用 `evaluation.rag_quality` 的冻结 v2 数据、N06/N07 和 `dev_calibration` 的 101 点阈值校准；`run_semantic_retrieval.py` 的 dev/test 分离，test 只跑一次。结果：B0 Recall@5 9/21、FPR 8/9；semantic/hybrid Recall 7/21、FPR 3/9、citation precision 7/10；生产默认未切换。测试见 `tests/test_h2_5_semantic_retrieval.py`。


## RAG 与 Memory

build_shared_rag_tools 提供 search_knowledge_base；mcp/tool_manager.py 保留改写、HTTP 检索、去重、重排、熔断和 fallback；KnowledgeBase 检索不缓存，重排后复核有效版本，其他工具缓存保留。mcp/rag_contract.py 定义文档与 citation/source contract；mcp/knowledge_base.py 使用外部 HttpClient 与版本化 collection，embedding 实现和 0.35 阈值未改。N06：管理员知识写入经 KnowledgeDocument → add_documents_async → _publish（publishing → 全部chunk核验/精确旧片段删除 → ready）；search 的 _eligible 在 Chroma Top-K 前筛选完整/生效/未废止/未被 supersedes 退役的 chunk IDs。同版本替换与跨版本退役语义分开；citation content_hash 与 reference 绑定实际文本。旧无发布记录资料需审核重发布，发布失败禁用该版本且需重试，不承诺跨进程或Chroma原子事务。接口与迁移边界见 `tests/test_knowledge_version_consistency.py`。N07：`_rerank` 返回带真实执行状态的 RerankResult，`_finalize_rag` 统一验证原候选与 citation/content_hash，再调用 N06 版本复核；无证据不返回 usable，正常 no_answer/low_confidence 为调用成功。`agents/tools.py`、BaseAgent Trace 与 `/search` 传递 rerank_status，跳过/fallback 不伪装 reranked=true；契约测试见 `tests/test_rerank_result_contract.py`。

api/main.py 的 collect_rag_evidence / render_rag_citations 继续向响应暴露可靠来源。citations 是检索证据，不代表逐句事实核验。memory/conversation_memory.py 按用户/会话读取 Redis 原始轮次、会话摘要和经 metadata 校验的 Chroma 咨询主题/偏好；memory/policy.py 仅从用户原话提取订单号、明确回复偏好及有限政策主题。达到 15 条时用 Redis transaction 留最近 5 条和确定性摘要，失败保留原始轮次。长期记录显式生成向量，按 user_id/source/type/有效期过滤；过期记录不会读入上下文，物理清理目前依靠内部删除接口，尚无定时任务。动态业务状态仍由 Provider 实时提供。

## Trace / API / Monitor 兼容性

/chat 和 /trace/tool/{request_id} 标记 topology=single、agent_type=support；agent_types=[support]。primary_agent、supporting_agents、routing_reason、routing_confidence 保留为 nullable deprecated API 字段并返回 null；intent、intent_group、intent_confidence、intent_source_scores 为空。没有伪造 general 路由。仓库内未发现前端依赖这些字段，外部消费者需适配 nullable 值。

core/model_observation.py 用 ContextVar 记录 Support 和 RAG SDK create 次数、usage、延迟和错误类型，不保存 prompt 或隐藏推理；不统计 Memory/profile、SDK 内部 HTTP 重试。SupportRuntime 保留有界 trace 和请求统计。PerformanceMonitor 检查 supports_routing=False，继续观测性能而跳过路由评分/建议。

## Eval 与历史 Multi

/eval/run 经 require_admin 后，由 evaluation/runtime.py 的 EvaluationRuntimeFactory 每轮创建独立 SupportRuntime、模拟业务 state、ActionService/Store 和 RAG 管理器；同轮读写 Backend 显式共享自己的 state。evaluation/evaluator.py 以局部 Runtime 执行，用固定模拟 customer-1 Principal 保留 Policy/HITL，不接聊天 Memory，Trace 也独立。构造或执行失败不会 fallback 到聊天 Runtime。LLM judge 只处理主观回复质量；默认不运行 intent cases，显式请求才诊断 IntentRecognizer。确定性 Tool/Policy/RAG/HITL 正确性仍通过专项 Eval 评分。

agents/agent_orchestrator.py 中旧 General / Technical / Billing / Escalation、Intent 路由、supporting 路径和 Composer 未物理删除，仅供历史测试和 evaluation/run_topology_comparison.py 实验使用。生产入口依赖该模块的 BaseAgent / 数据类型，不实例化 AgentOrchestrator。evaluation/topology_experiment.py 的实验 Single 保留原样。

T09/T10 dataset 和历史 report 内容未改。根目录 T09 JSON 已原样迁入 evaluation/reports/t09/，独立 FAQ 复验在 evaluation/reports/rag_http/；旧 manifest 文件名按历史来源解释。T10 最终 60 样本详见 evaluation/reports/t10_topology_comparison.md；supporting/composition 使用均为 0。失败 specialist 的 fallback 前调用由 T10 runner 完整记录，旧 Multi 最终 Trace 可能遗漏此证据的历史问题不在本次顺手修复。

evaluation/prepare_online_eval.py 与 capture_online_eval.py 的默认输入/输出统一为 data/evaluation/；历史证据与新运行分开。uv / pytest 缓存统一进入 cash/cache/，不移动 .venv 或运行模块。旧 Wiki、配图与差异说明已归档到本机 `cash/`。

## T12 Demo 与展示契约

`api/main.py` 的 GET `/demo` 返回 `demo/static/index.html`，`/demo-assets` 提供 JS/CSS/场景 JSON。`demo/static/demo.js` 消费 POST `/chat` 后按 request_id 查询既有 Trace；`view` 关联 citation 与 retrieval_hits 的文档标题。所有模型/工具文本通过 textContent 展示，不执行 HTML。旧 nullable routing 字段只在原始 JSON 中可见，不参与界面决策。
