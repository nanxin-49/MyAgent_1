# CartCare 业务流程说明

本文档从业务视角说明 CartCare 如何处理一次 HTTP 客服请求：什么时候先识别意图，什么时候切换 Agent，什么时候由 Agent 调用知识库工具，什么时候并行协作，什么时候压缩会话，什么时候更新用户画像，以及 Monitor 和 Eval 如何独立运行。

当前代码的主事实以 /chat 调用链为准。Provider、退款 Policy、HITL 和真实工单动作目前尚未接入。

## 1. 一次用户请求的完整流程

HTTP 客户端调用 /chat 后，系统按下面顺序处理：

~~~text
用户消息
  -> 读取记忆上下文
     - Redis 当前会话最近消息
     - ChromaDB 相关历史摘要
     - ChromaDB 用户画像
  -> 意图识别
     - LLM 语义理解
     - Embedding 相似度
     - Pattern 关键词兜底
     - 输出 intent、intent_group、实体和紧急度
  -> 构造 Request 并交给 AgentOrchestrator
  -> 生成 RoutingDecision
     - General / Technical / Billing / Escalation
     - 必要时主 Agent + 辅助 Agent 并行
  -> Agent 注入匹配的 Skills 并调用 LLM
     - 仅在模型选择且白名单允许时调用 search_knowledge_base
     - 工具调用最多 3 轮，结果回填给 LLM
  -> 写入用户消息和 Agent 回复
  -> 异步更新用户画像
  -> 返回 ChatResponse
~~~

RAG 不是 API 在路由前固定执行的阶段。Agent 选择 search_knowledge_base 后，工具层才执行查询改写、并行召回、合并去重、可选重排和 fallback。需要直接观察这条检索链路时，使用 /search。

/monitor 和 /metrics 提供运行时观测；Monitor 在应用生命周期中后台采集统计并反馈路由惩罚。/eval/run 是独立评测入口，不会被每次 /chat 自动调用。

## 2. 什么时候会切换 Agent

CartCare 并不是固定使用一个 Agent，而是根据用户问题动态选择。

### 2.1 技术问题切到 TechnicalAgent

当意图识别结果是 `technical`、`technical_login`、`technical_crash`，或者问题中包含明显技术关键词时，会切换到技术 Agent。

典型输入：

```text
应用一直报 401 错误
网页打不开
系统崩溃了
出现 500 error
无法登录
```

常见关键词：

```text
崩溃、报错、error、crash、无法登录、登录失败、500、401
```

业务效果：

```text
GeneralAgent -> TechnicalAgent
```

TechnicalAgent 会更倾向于给出排障步骤、错误原因和下一步处理建议。当前 TechnicalAgent 还会匹配 `skills/technical_support/SKILL.md`，在回复中遵循故障信息收集、错误码排查、部署配置检查、安全边界和二线升级规则。

### 2.2 账单/退款/账户问题切到 BillingAgent

当意图识别结果是 `billing`、`refund`、`invoice`、`payment_issue`、`account_security` 或 `account`，或者问题包含账单关键词时，会切换到账单 Agent。

典型输入：

```text
我要退款
为什么重复扣款了？
帮我开发票
我要取消订阅
修改我的邮箱
```

常见关键词：

```text
退款、扣款、发票、账单、支付、订阅、refund、invoice
```

业务效果：

```text
GeneralAgent -> BillingAgent
```

BillingAgent 会更关注退款、发票、订阅、账户资料等问题。当前 BillingAgent 还会匹配 `skills/billing_support/SKILL.md`，在回复中遵循账单核验、退款审核、发票处理和敏感信息保护等规则。

### 2.3 普通咨询使用 GeneralAgent

如果问题没有明确落到技术或账单领域，会默认使用 GeneralAgent。

典型输入：

```text
你好
你们支持哪些功能？
订单什么时候到？
怎么联系客服？
```

订单状态和物流问题会保留细粒度意图，例如 `order_status`、`logistics`，但归一化意图组会落到 `query`，默认仍由 GeneralAgent 处理。

业务效果：

```text
GeneralAgent
```

GeneralAgent 负责通用问答和简单引导。当前 GeneralAgent 还会匹配 `skills/general_customer_service/SKILL.md`，在回复中遵循首轮接待、信息澄清、问题分流、投诉升级和禁止索取敏感信息等规则。

### 2.4 转人工或高紧急度会触发升级

如果用户明确要求转人工，或者问题被识别为紧急，会触发升级标记。细粒度意图 `human_handoff` 会归一化为 `escalation` 意图组。

典型输入：

```text
我要转人工
我要投诉
找你们经理
非常紧急，马上处理
```

业务效果：

```text
escalated = true
```

当前项目里升级是标记状态；生产系统中可以在这个位置接入工单系统、人工客服队列或告警通知。

## 3. 什么时候会多 Agent 并行协作

如果一句话同时涉及多个业务领域，系统会先计算各领域分数确定 `primary_agent`，再通过 `_collaboration_targets()` 检测明确的技术、账单领域信号，将命中的其他专业 Agent 加入 `supporting_agents`。这样不会因为主 Agent 分数较高而误过滤已明确识别出的辅助领域。

当前参与打分的领域包括：

| 领域 | 对应 Agent | 主要证据 |
|------|------------|----------|
| `general` | GeneralAgent | 查询、订单、物流、会员、普通咨询 |
| `technical` | TechnicalAgent | 登录失败、401/500、崩溃、报错、错误码实体 |
| `billing` | BillingAgent | 退款、扣款、发票、支付、金额实体 |

对于关键词或意图明确命中的复合领域：

```text
命中的专业领域 -> supporting_agents
primary_agent 不重复加入 supporting_agents
GeneralAgent 不作为 supporting_agents
```

如果没有明确的复合领域信号，系统仍保留领域分数阈值作为弱实体信号的兜底判断。

### 3.1 技术 + 账单复合问题

典型输入：

```text
登录报错 401，而且这个月还重复扣款了
```

系统会识别到：

```text
技术问题：登录报错 401
账单问题：重复扣款
```

业务处理：

```text
primary_agent = technical
supporting_agents = [billing]
TechnicalAgent + BillingAgent 并行处理
```

返回形式类似：

```text
[technical - 主处理]
针对 401 登录错误的排查步骤...

[billing - 辅助处理]
针对重复扣款的处理建议...
```

### 3.2 为什么要并行而不是只选一个 Agent

如果只选 TechnicalAgent，账单问题可能被忽略；如果只选 BillingAgent，登录问题可能无法解决。

并行协作的价值：

| 业务问题 | 并行协作的收益 |
|----------|----------------|
| 一个问题跨多个领域 | 避免漏答 |
| 用户一次性提出多个诉求 | 分领域处理，更完整 |
| 专属 Agent 能力不同 | 主 Agent 负责主要诉求，辅助 Agent 补充相关专业意见 |
| 需要可观测路由 | 返回 `primary_agent`、`supporting_agents`、`routing_reason` 和领域分数 |

## 4. 什么时候会降级到 GeneralAgent

降级是系统可靠性策略。即使专属 Agent 出问题，也尽量给用户一个通用答复。

会降级的情况：

| 情况 | 结果 |
|------|------|
| 目标 Agent 类型没有可用实例 | 使用 GeneralAgent |
| TechnicalAgent 执行失败 | 降级到 GeneralAgent |
| BillingAgent 执行失败 | 降级到 GeneralAgent |
| LLM 调用异常 | 返回通用错误提示 |

业务效果：

```text
专属 Agent 失败 -> GeneralAgent 兜底
```

这样用户不会直接看到系统崩溃，而是收到“稍后重试”或通用处理建议。

## 5. 什么时候会话会被压缩

CartCare 会把当前会话最近消息存在 Redis 中，叫工作记忆。

默认规则：

```text
WORKING_MAX = 20
COMPRESS_AT = 15
```

当同一个 `user_id + conv_id` 的工作记忆达到 15 条消息时，会触发压缩。

### 5.1 压缩前

Redis 中可能有很多轮消息：

```text
user: 你好
assistant: 你好，请问有什么可以帮你？
user: 我要退款
assistant: 请提供订单号
...
```

### 5.2 压缩时

系统会：

```text
旧消息 -> LLM 总结 -> 会话摘要
```

然后执行三件事：

```text
1. 摘要写入 Redis summary:{user_id}:{conv_id}
2. 摘要写入 ChromaDB episodic
3. Redis 工作记忆只保留最近 5 条
```

### 5.3 压缩后

后续对话上下文由三部分组成：

```text
会话摘要
相关历史
最近 5 条消息
```

业务价值：

| 问题 | 压缩带来的收益 |
|------|----------------|
| 对话太长 | 控制 prompt 长度 |
| 历史信息不能丢 | 用摘要保留关键信息 |
| 后续还要查历史 | 写入 ChromaDB 供语义检索 |

## 6. 什么时候会更新用户画像

每次 `/chat` 回复完成后，系统都会异步更新用户画像。

触发时机：

```text
Agent 回复完成 -> 写入本轮对话 -> 后台更新用户画像
```

画像内容示例：

```json
{
  "preferences": ["喜欢简洁回答", "经常咨询退款"],
  "entities": {
    "产品": ["会员服务"],
    "问题类型": ["账单", "登录"]
  }
}
```

业务作用：

| 用户画像信息 | 后续作用 |
|--------------|----------|
| 偏好 | 让回复更贴近用户习惯 |
| 常见产品 | 帮助 Agent 理解用户上下文 |
| 常见问题类型 | 帮助后续回复更聚焦 |

注意：用户画像更新是异步执行的，不会阻塞当前回复。

## 7. 什么时候会查询知识库

知识库现在有两种入口：

| 入口 | 用途 |
|------|------|
| /chat | Agent 按需调用 search_knowledge_base，使用知识库结果生成回复 |
| /search | 直接调试查询改写、并行召回、去重、重排和 Top-K |

/chat 的实际 RAG 路径是：

~~~text
/chat
  -> IntentRecognizer 结果进入 Orchestrator
  -> Agent 获得 search_knowledge_base 工具
  -> 模型决定是否调用该工具
  -> MCPToolManager.search_with_rewrite()
       -> LLM 查询改写
       -> 子查询并行调用 knowledge_search
       -> 合并去重
       -> 可选 LLM 重排
       -> 返回结果给 Agent
  -> Agent 继续生成回复
~~~

工具白名单允许四类 Agent 使用共享 RAG 工具，但是否实际检索由模型的 tool_use 决定。greeting、feedback、human_handoff 等请求通常不会触发检索；不能把“业务类问题会检索”理解为 API 层必然执行。

当知识库工具失败时，ToolManager 可返回 fallback 或结构化错误，Agent 继续按照结果生成可解释回复。RAG 只承载政策、FAQ 等静态或半静态知识；订单状态、物流、库存、支付和退款状态目前没有接入 Provider。

### 7.1 /search 与 /chat 的区别

~~~text
/search
  -> 直接进入 MCPToolManager.search_with_rewrite()
  -> 返回 results / reranked
/chat
  -> 先完成记忆、意图和路由
  -> 仅当 Agent 发出 search_knowledge_base tool_use 时进入同一检索管理器
  -> 将 tool_result 回填给 Agent
~~~

这两个入口都使用 ChromaDB knowledge_base，但只有 /chat 会把检索结果作为 Agent 工具结果继续生成对话回复。

## 8. 什么时候会加载和注入 Skills

Skills 是可热加载的业务处理规范，和知识库互补：

| 类型 | 解决的问题 | 示例 |
|------|------------|------|
| 知识库 | 业务事实是什么 | 退款政策、配送说明、会员规则 |
| Skills | 客服应该怎么处理 | 如何澄清信息、何时转人工、哪些话不能说 |

启动时，`api/main.py` 会创建 `SkillManager`，从 `ECHOMIND_SKILLS_DIR` 指向的目录加载 Skills。默认目录是项目内 `./skills`。

当前内置三类 Skills：

| Skill | 适用 Agent | 触发方式 |
|-------|------------|----------|
| `general_customer_service` | GeneralAgent | 命中咨询、售后、客服、投诉、转人工等关键词 |
| `technical_support` | TechnicalAgent | 命中报错、接口、API、部署、日志、500、401 等关键词 |
| `billing_support` | BillingAgent | 命中退款、扣款、发票、订阅、支付、账单等关键词 |

注入流程：

```text
用户消息
  -> Orchestrator 选择 Agent
  -> BaseAgent._build_system_prompt()
  -> SkillManager.prompt_for(message, agent_type)
  -> 遍历已加载的 Skills
  -> 筛选 enabled=true 的 Skill
  -> 检查 Skill front matter 中的 agents 是否包含当前 agent_type
  -> 检查用户消息是否命中 keywords
  -> 拼入 system prompt 的 [动态 Skills] 区块
```

### 8.1 通用 Agent 加载 Skills 的具体例子

如果用户消息是：

```text
你好，我想咨询售后处理进度
```

系统先识别为普通咨询，路由到 `GeneralAgent`。随后执行：

```text
GeneralAgent
  -> agent_type.value = "general"
  -> BaseAgent._build_system_prompt(req)
  -> SkillManager.prompt_for("你好，我想咨询售后处理进度", "general")
```

`SkillManager` 会检查 `skills/general_customer_service/SKILL.md` 顶部的配置：

```yaml
agents: general
keywords: 你好,您好,咨询,帮助,客服,订单,售后,活动,会员,账户,资料,投诉,建议,人工,转人工,处理进度,服务
enabled: true
```

这个 Skill 同时满足三个条件：

| 条件 | 当前结果 |
|------|----------|
| `enabled=true` | 满足 |
| `agents` 包含 `general` | 满足 |
| 用户消息命中 `你好`、`咨询`、`售后` 或 `处理进度` | 满足 |

因此 `通用客服接待规范` 会被拼入 `GeneralAgent` 的 system prompt。

如果同一条消息路由到 `TechnicalAgent`，由于 `general_customer_service` 的 `agents` 不包含 `technical`，它不会被注入。这个设计用来避免通用客服规则、技术排障规则和账单退款规则互相污染。

如果修改了 Skill 文件，可以调用：

```bash
curl -X POST http://localhost:8000/skills/reload
```

系统会重新扫描 Skill 目录，不需要重启服务。

查看当前加载状态：

```bash
curl http://localhost:8000/skills
```

返回内容会包含 Skill 名称、描述、文件路径、关键词、适用 Agent、是否启用和解析错误列表。

## 9. 什么时候 Monitor 会影响路由

Monitor 每 10 秒采集一次 Agent 和工具表现。

采集指标：

```text
Agent 成功率
Agent 平均延迟
工具成功率
工具平均延迟
工具连续失败次数
```

如果某个 Agent 成功率低或延迟高，Monitor 会计算 `monitor_penalty` 并写回 Orchestrator。

路由分数：

```text
base_score = success_rate * 0.7 + latency_score * 0.3
routing_score = base_score * (1 - monitor_penalty)
```

业务效果：

```text
表现差的 Agent -> routing_score 降低 -> 后续更少被选中
```

如果同一类 Agent 未来扩展成多个实例，这个机制可以自动选择表现更好的实例。

## 10. 常见业务场景示例

### 场景一：普通问候

```text
用户：你好
Agent：GeneralAgent
结果：普通欢迎语
```

### 场景二：技术故障

```text
用户：应用登录一直报 401
Agent：TechnicalAgent
Skills：注入技术支持处理规范
结果：给出登录失败排查步骤，并提醒不要公开 Token、密码或验证码
```

### 场景三：退款问题

```text
用户：我要退款，为什么还没到账？
Agent：BillingAgent
结果：说明退款审核和到账周期
```

### 场景四：技术 + 账单复合问题

```text
用户：登录报错 401，而且还重复扣款了
Agent：primary_agent + supporting_agents，例如 TechnicalAgent 主处理，BillingAgent 辅助处理
结果：两个 Agent 并行回复后按主处理、辅助处理合并
```

### 场景五：账单 Skill 约束退款承诺

```text
用户：我要退款，今天必须到账
Agent：BillingAgent
Skills：注入账单退款处理规范
结果：说明需要先核验订单和支付渠道，不承诺“今天一定到账”
```

### 场景六：长对话

```text
用户连续对话超过 15 条消息
系统：触发工作记忆压缩
结果：旧消息变成摘要，最近 5 条继续保留
```

### 场景七：强烈投诉

```text
用户：我要投诉，马上转人工
系统：标记 escalated = true
结果：生产环境可转工单或人工客服
```

## 11. 业务规则速查表

| 触发条件 | 系统行为 |
|----------|----------|
| 普通咨询 | 使用 GeneralAgent |
| 技术关键词或 technical 意图 | 使用 TechnicalAgent |
| 退款/扣款/发票/订阅/账户问题 | 使用 BillingAgent |
| GeneralAgent 处理普通咨询 | 注入通用客服接待规范 Skill |
| TechnicalAgent 处理技术问题 | 注入技术支持处理规范 Skill |
| BillingAgent 处理账单问题 | 注入账单退款处理规范 Skill |
| 修改 Skill 文件 | 调用 `/skills/reload` 热加载 |
| 技术 + 账单分数都达到阈值 | 多 Agent 并行协作，返回主 Agent 和辅助 Agent |
| 专属 Agent 失败 | 降级到 GeneralAgent |
| 用户要求转人工 | 标记 `escalated = true` |
| 工作记忆达到 15 条 | 压缩旧消息，保留最近 5 条 |
| 每次回复完成 | 异步更新用户画像 |
| Agent 成功率低或延迟高 | Monitor 写回降权，降低 routing_score |
| Agent 通过 /chat 发出 search_knowledge_base tool_use | 检索结果作为 tool_result 回填给 Agent |
| 知识库不可用 | 项目自研工具层返回 fallback 降级结果，主对话继续运行 |
