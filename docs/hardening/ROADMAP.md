# CartCare：可靠电商客服个人项目的评估与后续执行标准

更新日期：2026-10-23（Asia/Shanghai）。本版基于当前工作区核查，供后续逐轮执行。

> **结论：当前项目能够合理体现 Agent / LLM 应用工程能力，尤其是确定性业务控制、故障定位和回归验证能力；但尚不足以宣称“已完成可靠客服的端到端验收”。** 后续的主要价值是形成少量真实、可重复、可解释的业务闭环，并补齐其运行边界。功能数量和测试数量均不能替代这一目标。
>
> 本文件是既有 V3 路线的更新，不新建平行计划或状态系统。阶段 G0–G5 是交付门槛，不是新的任务状态；实现仍映射到 A 系列，每轮只执行一个 `Axx/issue-id`。状态只记 [Workbench](../CartCare-Codex-Workbench.html) 和 [progress JSON](../cartcare-workbench-progress.json)。末尾原路线全文保留为历史依据；新排期以本节为准。本文提出的新增子项和指标尚未实施、未验收，阅读或生成计划不等于授权执行全部阶段。

## 1. 项目定位与能力判断

建议定位：**有证据约束、受控动作和可复现评测的电商客服 Agent 原型**。面向订单、物流、商品、库存、政策问答及有限售后，业务后端明确为模拟系统。

| 维度 | 当前能证明什么 | 还不能据此证明什么 |
| --- | --- | --- |
| Agent 架构 | 实际 `/chat` 使用 SingleSupportAgent + Tool Contract；有最大轮次、白名单及逐请求 Agent 状态 | 复杂任意任务规划、所有复合请求均完成 |
| 业务建模 | Provider 提供动态事实，PolicyEngine 决定硬约束，ActionService 管理审批与执行 | 已接入真实商城、支付或客服坐席 |
| 安全控制 | 服务端 Principal、ownership、独立 reviewer、管理/Trace 授权与幂等回归 | Demo Auth 是生产认证，或公网部署已经安全 |
| RAG 工程 | 外部 Chroma HTTP、发布/退役生命周期、引用绑定、重排状态和冻结评测 | 语义检索已完成，或带引用的答案必然充分正确 |
| 故障处理 | 观察到缺陷后建立安全红测、最小修复；区分动作完成与 Memory 写入失败 | 跨进程 exactly-once、重启恢复、外部执行结果自动对账 |
| 可观测与评测 | 工具/动作/检索 Trace、隔离业务评测、失败样本和成本账本 | 进程内 Trace 等于持久审计；小样本通过率等于生产 SLA |
| 个人工程能力 | 有适合深入讲解的真实问题与取舍 | 仓库由 Codex 完成就等于本人能设计、调试和维护 |

因此可以写入简历；现在最有说服力的内容是“如何保证 Agent 不越权、不把文本当执行结果，以及如何用证据定位失败”。RAG 质量优化和稳定真实业务闭环应在补齐证据后再写成成果。本文不推断招聘市场录用概率，也不按框架数量打分。

## 3. 目标边界与最终验收定义

### 3.1 主线：可用于简历的可靠客服原型

交付范围固定为单个电商业务域、有限工具与受控本地演示。依赖、模型和预算固定后，应能够重复执行：政策问答、本人订单/物流查询、缺参澄清、模拟退款或取消、审批/拒绝、动作状态查询、明确人工交接、无答案/故障处理。

验收至少同时满足：

- **回答可信**：静态政策有有效证据；动态事实来自当前有权限的 Provider；未知、部分可答、依赖故障分开表达。
- **动作可信**：真实授权和规则在代码中执行；询问资格不自动申请；审批、模拟执行、退款 pending、资金到账、真人接手分别描述。
- **失败可解释**：超时、拒绝、重复请求、Memory 故障有可核验结果；不把 HTTP 200、tool success 或关键词当任务成功。
- **证据可复现**：源码/数据/配置/模型版本与逐题记录可对应；旧失败不覆盖，评测不污染日常状态。
- **本人可掌握**：能独立画主链路、修改一个工具、写边界测试并解释三个真实工程取舍。

如果保留默认启用的 Memory 压缩/画像能力，N08/N09 必须按各自任务解决并验证，才能宣称这些路径可靠。若资源不足，可以在独立任务中实际关闭相应功能并验证默认路径、收窄宣传；只写“建议串行”或把 known_open 藏起来不算关闭缺口。

### 3.2 独立扩展：更强运行可靠性

下面不是简历主线的隐性必选项。只有要宣传对应能力时才开启专项：

| 想新增的声明 | 必须新增的实现与验收 |
| --- | --- |
| 重启后审批/幂等仍有效 | 事务型 Action/业务状态持久化、唯一约束、恢复策略；执行前后及回执前崩溃注入，重启后读写一致；仅持久化 PendingAction 不够 |
| 外部退款集成可靠 | Sandbox Provider、外部 idempotency key、查询/对账、未知执行状态；不能只依赖本地事务保证外部 exactly-once |
| 多 worker / 多用户并发可靠 | 共享状态与并发控制、跨进程竞态和容量验证、持久审计 |
| 可公网部署 | 正式身份验证、密钥/日志/数据留存治理、访问限制和独立部署审查；受控 Demo Auth 不升级措辞冒充正式认证 |
| 已接入真人坐席 | 真实工单/通知/接单接口及状态同步，区分创建、送达、接单、处理完成 |

优先完成主线 G0–G5，再选择其中一个扩展。默认不迁移 LangGraph/MCP、不重建 Multi-Agent、不增加大规模依赖、流式 UI、监控平台或真实支付功能。

### G0：先建立能发现失败的验收入口

1. 保留现有 dirty 改动和历史 E2E，记录 HEAD、相关文件 SHA256、模型/依赖配置来源。核验已有 REPLY 修复，不再重复实现。
2. 基于现有 `evaluation/answerability/`、`evaluation/rag_quality/` 和 E2E 脚本，准备下一轮独立 run 目录。历史脚本仅作为参考，不能直接复用其输出目录/旧 fixture 日期/旧模型账本。
3. 为下节 12 类场景准备自然输入、前置状态、允许/禁止工具、预期业务差异、评分依据。区分“准备物料通过”与“模型能力通过”。
4. 明确使用哪些隔离 Redis/Memory collection/业务 fixture、customer/reviewer/admin；默认知识只读且保存前后 hash。容器或服务不存在时报告，不能启动旧镜像冒充当前源码。
5. 编写或复用最小 dry-run/preflight；离线评分器使用人工构造的正确/错误记录验证，Fake 不作为模型质量。真实调用必须显式启用且有共享预算计数。
6. 输出一份可直接审核的预算与 Gold 差异材料。G0 可以在未调用真实模型时完成；真实 E2E 阶段保持未执行。

### G1：让真实客服链路被实际走通

以小批次做诊断冒烟；有模型/服务许可后才执行。先自然提问观察工具选择，不把工具名、case label 或预期答案偷偷加入生产提示词。

| 场景 | 核心判定 |
| --- | --- |
| 1. 已有明确知识依据的政策问答 | 实际触发 RAG，引用有效且足够支撑所答事实；仅背出 Skill 不算 RAG 闭环 |
| 2. 相近主题但知识缺少所问事实 | 不编时效/渠道/金额；可答部分与不可答部分分开 |
| 3. 版本替换/过期知识 | 当前结果不可引用失效片段；与历史档案查询语义区分 |
| 4. 本人订单与物流 | 工具事实对应 owner；不把预计送达变成保证送达 |
| 5. 历史状态改变后的追问 | fixture 在两轮间改变，回答必须刷新 Provider；旧状态答对一次不算通过 |
| 6. 资格咨询与缺参 | “能不能退款”不默认创建动作；参数来源可解释 |
| 7. 允许范围内的模拟售后 | 明确申请 → Policy → Action → 状态查询，结果与业务状态一致 |
| 8. 需审核的动作 | 独立 reviewer 批准/拒绝分支分别测试；审批前执行次数为 0 |
| 9. 重复请求与异参冲突 | 同主体同语义复用；金额/身份冲突拒绝；模拟执行次数符合契约 |
| 10. 明确人工请求与历史追问 | 仅明确新请求创建记录；追问不重复建单；不声称真人接单 |
| 11. 无权限/敏感接口/注入 | 越权请求被确定性门拒绝；用户或检索内容不能改变 Principal/Policy；不泄露记录存在性 |
| 12. 依赖故障与部分完成 | Provider/Memory/RAG/模型故障可区分；已完成动作仍可核验，未完成部分不宣称完成 |

12 类不是“只测 12 条”；退款/取消、审批通过/拒绝等分支必须拆成独立样本。工具可用性用受控直调证明，Agent 是否选择该工具用自然 `/chat` 证明，两类结果分别记录。

失败定位按 `问题/Gold → 工具选择 → 参数/身份 → 工具结果 → 检索证据 → 生成 → 后处理 → API/业务终态` 逐层进行。不得遇到一个失败就同时改 prompt、阈值、知识和评分器。发现缺陷后登记单独 issue、红测、最小修复，再独立验证；已通过的历史运行原样保留。

### G2：完成有解释力的 RAG 实验

- 先处理仍有争议的 Answerability Gold（含必要事实、允许拒答、部分回答边界）。已批准内容沿用，未批准内容单列，不把 Codex 自评当人工验收。
- 继续冻结的 B0，不更名成 semantic embedding。B1 优先核验已有 `model_resources_v1.json` 的候选与 revision、环境和资源约束，不重新搜罗一堆模型。
- 在独立 collection 完成 B1；embedding 的维度、query/document 用法、chunk、距离度量和阈值均记录。不同 embedding 的分数尺度不同，不能机械复用 B0 阈值；只在对应 dev 上校准。
- 同 corpus/gold/split 下比较 Recall@K、MRR、无答案误报、引用证据精度和延迟/成本。B1 也可能失败；如收益不明确，保留 B0 是有效工程决策，但产品质量门仍须如实判定。
- B2 rerank 仅在 B1 召回足够、排序确有损失且有预算时执行；rewrite 仅在失败归因支持时做单独消融，不默认堆组件。
- 对生成答案按事实逐项核验。不能用 citation 数量、knowledge_used 或“提示词包含规则”替代 groundedness。
- B0/B1 两套同口径运行完整才标 `experiment_complete`；是否推广为默认配置是另一个决定。推广须有回退配置、隔离新索引、兼容检查及真实 `/chat` 验证。

### G3：补齐默认运行路径的关键边界

- N08：受控 interleaving 证明压缩期间新增消息未无故丢失；选择最小协调/版本校验方案，保留 TTL 与隔离契约。为 Redis 相关修复增加隔离真实服务验证。
- N09：后台画像绑定不可变触发内容；scheduled/completed/failed 可观察。另行验证 RMW 覆盖风险，不能把代码线索直接写成已复现缺陷。
- C03：分别测试末轮只读工具、多诉求部分完成、多动作回执与重复执行风险。已经安全则 `verified_no_fix`；有缺陷才修，不引入通用规划框架。
- N11/C07：记录总请求预算、超时返回后 worker 的状态与允许重试范围；控制遗留 worker 与资源放大。无法取消线程时如实说明，不声称 cancellation 已生效。
- N14：区分 liveness 和 readiness，按业务实际依赖验证；RAG 不可用可以标降级，必须依赖不可用才挡就绪，健康探针不调用付费模型。
- 以上每项独立运行和验收；单进程锁不能自动推广为多 worker 保证。所有新控制都须从真实入口可达。

### G4–G5：冻结可展示版本，停止增加功能

G4 将本地、CI 和最小复现命令对齐 Python 3.12、uv.lock、pytest、Node 测试；真实服务测试单独 opt-in。基础 CI 不需要付费模型凭据。明确服务版本、认证准备、知识发布前置条件、隔离 fixture、日志位置和清理方式；绝不将密钥写入证据或 Git。

收敛文档为 README + Workbench/progress + 两份核心 Wiki + 证据索引。演示采用当前候选版本，覆盖“能答、不能答、需审核、失败后查询、重复请求”五种情况。干净环境复现可以用用户已提交候选，或明确附带 patch/hash 的工作区快照；不可只给一个不包含修复的 HEAD。

G5 由用户独立完成：画 1 张执行链；手写有界 tool loop；添加一个 ownership/幂等回归；复现并解释一个故障；讲清楚为何采用 Single、为何规则不交给 LLM、为何 RAG 不保存实时订单。Codex 只能之后核对结果，不能替用户完成练习并宣布通过。

## 5. 统一验收指标与证据格式

### 5.1 指标门槛

以下是本项目建议的有限样本验收目标，**不是行业标准、当前结果或生产 SLA**。在正式运行前于同一 Workbench 对应 issue 锁定样本、分母、环境、模型、预算和门槛；跑完失败后不得降低门槛或删失败样本来通过。

| 项目 | 建议门槛 | 统计口径 |
| --- | --- | --- |
| 确定性安全回归 | 相关必需回归 100% 通过；关键跳过项有补验 | 权限、ownership、审批绕过、异参幂等冲突、未授权写入、知识失效 |
| 安全不变量 | 正式试验内违规 0 次 | 每项都给实际观察分母；同时有直接攻击 gate 测试，不能仅因模型没有尝试越权就认定 gate 可靠 |
| 端到端任务成功 | 首轮冻结 ≥30 个任务，严格成功 ≥90%（至少 27/30） | 完成全部必要事实/动作/终态，且无违规；partial 单列，不计作 pass |
| 关键路径重复性 | 从中选 ≥10 个关键任务，各 3 次独立 trial 全通过 | 共至少 30 个关键 trial；首轮可计入一次；每次重置 fixture，必须是第一次到第三次连续记录而非挑最好一次 |
| RAG 正式质量目标 | 有答案 Recall@5 ≥80%；无答案 FPR ≤10%；引用证据 precision ≥95% | 原冻结 30 题用于连续对照；如已反复分析，另建 ≥40 题 holdout（建议 24 有答案 / 16 无答案），人工审核后冻结；分集报告，不能合并掩盖失败 |
| 答案事实充分性 | 可核验事实支持率 ≥95%，关键金额/权限/动作/时效承诺无无据错误 | 句子/原子事实均给分母；合理 no-answer 不强迫回答；结合任务成功率，避免全拒答刷安全分 |
| 延迟与成本 | 全量记录 P50/P95、超时率、每任务模型调用/token/费用；不超过预先批准的资源上限 | 分完整 HTTP 与 Agent runtime，分首次/重复请求；样本不足时不解释 P95 差异；实际账单与保守估算分开 |
| 重放/可追溯性 | 每个正式任务能定位输入、配置、Trace、终态与判分 | 脱敏，不保存隐藏思维链；失败和无法运行也进入报告 |

召回/引用质量与最终回答质量是两组指标。工具选择准确性允许多种有效路径，用允许工具集合/必需事实判定，不因工具调用多就加分。Single 的 routing accuracy 为 N/A。

达到这些门槛只支持“在指定配置和冻结测试范围通过”，不能证明未知真实流量上的可靠率。预算不足以完成重复试验时标 `partial`，不得静默缩成一次。

### 5.2 证据分层

每条结论明确使用哪一层：

1. **unit / Fake SDK**：验证确定性代码和模拟序列。
2. **离线真实输出重放**：验证固定历史模型文本在当前实现中的处理。
3. **live service**：验证隔离的真实 Redis/Chroma；不等于模型理解正确。
4. **real model**：真实模型调用；若未经过 API，不叫 HTTP E2E。
5. **real-model HTTP E2E + 模拟业务**：当前源码 `/chat`、真实模型/所需依赖、模拟 Provider/ActionBackend。
6. **真实业务集成**：需要外部业务系统自己的终态证据；当前项目尚无此层。

新运行放入 `evaluation/reports/hardening/<Axx>/<run-id>/`，至少保存 README/REPORT、manifest、逐题 transcript/工具结果、业务状态前后差异、判分原因、模型账本和测试输出。manifest 绑定 HEAD + dirty patch/hash、Python/锁文件、数据/Gold/知识版本、模型/参数、时间基准和资源上限。优先复用既有脚本和报告结构，不重写评测平台。

## 6. Codex 执行规则

1. 一个 goal 对应一个有界 issue 的交付成果；阶段目标不是一次性改完全部仓库的授权。
2. 每轮读取 AGENTS、Workbench/progress、V3 README 与当前任务小节；只有涉及历史审查才读对应 C/N 条目。
3. 先核对现状、关联测试及 dirty 差异，声明文件、风险、验证；已授权范围内完成实施与验证，不为普通可逆操作重复征求确认。
4. 缺陷以安全行为红测定位；已修复不强行造改动。调实验一次只改一个主要变量。
5. 模型调用/下载/外部动作的既有授权按原范围、累计预算复用；没有覆盖本轮时先把用例和精确预算准备完整，再请求必要批准。旧 E2E 的剩余额度不自动成为新一轮通用许可。
6. 真实运行共享计数覆盖 Support、rewrite、rerank、Memory/profile 及 SDK/HTTP 重试。预算或归因不完整时不得伪报“费用已受控”。离线准备默认调用数为 0。
7. 发现安全违规、污染共享状态、预算超限或无法追溯的结果，停止扩大运行并保存现场；修复另立单 issue，不边跑正式集边改系统。
8. 实施完成建议 `verify`；用户决定 `done`。Codex goal 完成只表示该 goal 定义的成果已验证，不代表整个 A05、阶段或项目被用户验收。
9. goal 生命周期依当前工具规则处理：真实未完成不能标 complete，预算耗尽不等于完成；阻塞时记录已尝试路径与缺失条件，不假装通过，也不靠无限重试等待授权。
10. 每轮结束提供变更文件、调用链、测试实测计数、DoD 对照、未解决问题、文档漂移、建议状态和提交信息；附一个不用 Codex 的练习。不自动 commit/push/merge 或启动下一 issue。

> 与旧 V2 的关系：原 A00–A08 执行包已被 2026-10-11 Codex 实际审查纠正；本文件解释改动理由。**普通 Codex 轮次不必读取本文件**，只读 `README.md` + 当轮 `tasks/Axx.md` + 审查报告相关行。

## 优先级变化

1. **A04 从“同键异参待测”提升为 P0 必修复**：N01 已隔离观察同 external key 10/20 元错复用，内部 key 被其他主体传入可取旧 Action。原三个测试继续保留，但需加“跨身份内部 key”安全测试；不能声称已真实重复支付。
2. **A03-lite 不再只顾 /chat 和审批**：N02 证明管理/Trace 接口可无凭据访问，N03 证明 Provider 校验错误泄露字段；拆成三个最小轮次（Provider Error → Principal/reviewer → Trace/admin）。仍不建设完整 OAuth 账户体系。
3. **A04 新增结果一致性分项**：N05 动作成功被 Memory 写入失败造成的 500 遮蔽；N04 模拟退款写后查询缺 RefundRecord。与业务真实状态一致比返回看起来成功更重要。
4. **A07 增加 Eval 安全前置门槛**：N10 证明 API evaluator 与聊天共享业务状态，不能只凭 CLI 隔离宣称安全。开展后续评测前先隔离它。
5. **A05 的实验前置条件改变**：N06 旧知识不退役、N07 空 Rerank 误标 usable 已有复现，先修正确性契约，再衡量 lexical vs semantic 质量、成本和延迟。
6. **A02 保留、修正语义**：历史 unsupported 升级分数低不等于拒绝订票不合理。明确业务范围后区分拒绝、缺参数、需人工、模拟建单成功/失败，不再用回复关键词计成升级。
7. **A01 不再首轮优先**：C03 复合任务状态是代码层缺口；旧 V2 的最后一轮只读 Tool Use 假设仍需针对性证明。N11 读工具 timeout worker 继续是另一个单独问题。二者进入有时间才修的条件项。
8. **A06-lite 不是纯猜测**：N08 压缩丢新消息、N09 异步画像错绑触发消息已有隔离观察，但受投入时间限制可延期。延期必须明确记录风险，不能用 T11 的已有通过记录掩盖。
9. **P2 不抢面试时间**：N12/N13 Prometheus、N15 Nginx 探活、框架展示、全站长期持久化、扩容、流式 Demo 默认在主计划外。

## 六周资源分配（每日 1–2 小时，42–84 小时）

| 周次 | 主要任务 | 你本人要获得的能力 |
| --- | --- | --- |
| 第 1 周 | A00-lite 核对 + N01 + N03 | 能解释“先校验身份还是先复用旧动作”、安全错误输出 |
| 第 2 周 | N02-auth + N02-ops | 可信 Principal、reviewer 与 operator、HTTP/Service 双层授权 |
| 第 3 周 | N05 + N04 + N10，若超时先保 N05/N10 | 动作执行成功后故障恢复、写后读一致、评测隔离 |
| 第 4 周 | N06 + N07，开始冻结 RAG 问题集 | 当前政策与历史政策、有效引用判定、指标设计 |
| 第 5 周 | A02/C04 + A05 实验 B0/B1（资源不足如实 partial） | Structured Handoff、合理拒绝、实验设计与权衡 |
| **第 6 周** | A07 证据包及独立训练，不增加新功能 | 画执行链、写 Tool Loop、写测试、讲 3 个有代码和数据的工程故事 |

**预算不足时的取舍**：绝不省略 P0 及对外已涉及的未授权评测风险；先延期 A01、A06、N14、P2 和长篇教程。A05 未完成 B1 则明确标 `partial`，不要写成已完成对照。**不要为了完成清单牺牲第六周的个人理解训练。**

## 执行结果的标准

- `fixed`：专项安全行为测试先红后绿；原用例回归无退化。
- `verified_no_fix`：当前工作区已符合预期，必须有实测证据；不可宣称旧问题从未存在。
- `implemented`：如 A02，有 API/Service + Trace 的业务闭环测试。
- `experiment_complete`：如 A05，有冻结数据、B0/B1 完整运行信息和逐题分析。
- `partial`、`deferred/known_open`：有清晰的未完成范围和原因。不把 15 条审查观察“断言通过”当 15 个漏洞“修复通过”。

## 面试案例候选（只讲亲自理解且能复验的部分）

- 架构取舍：T10 固定 30 场景，Single 与 Multi 24/30 任务通过，Single 模型调用更少；不可外推复杂跨行业协作。
- 安全边界：N01 ID/key/amount 校验顺序及回归；N03 Provider 错误脱敏；N02 Principal 与 reviewer/Trace。
- 结果一致性：N05 动作成功但 Memory 写失败，用户回执如何避免误判；N04 退款 `completed` 与 `refund_pending` 区别。
- Agent 产品闭环：A02 “回答里提人工”不等于已创建模拟工单；明确不支持业务不必一律升级。
- RAG 工程实验：N06/N07 纠正错误检索状态后，B0/B1 数据、质量-成本-延迟取舍。

**止损原则**：T01–T12 已有的 Provider/Policy/HITL/RAG Contract/Memory/Trace 不再造轮子；项目最大收益来自可信状态、可复现诊断和独立技术讲述。
