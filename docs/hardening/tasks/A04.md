# A04｜ActionService：已证实的幂等与结果一致性问题

> **逐轮选择**：本文件包含 **N01、N05、N04** 三个独立问题。**一次 Codex 只执行一个**（例如 `A04/N01`）；切勿同时实施。保留原 ActionService、Policy、HITL、状态机和现有 Store，不默认引入 SQLite。

## A04/N01（P0，首先执行）——幂等错误复用与越权读取

**依据**：审查报告 N01 / `IDEMPOTENCY`；`actions/service.py:159,369`。隔离观察：同 external key 由 10 元改 20 元，却返回旧 10 元 Action；将响应中的 internal key 交给另一用户时取回原用户的 Action。**当前审查未观察到重复真实支付执行**，不要误述为此漏洞。

**红测设计**：
1. 同主体＋同外部 key＋同标准化参数 → 同 Action，副作用只发生一次。
2. 同主体＋同 key＋不同 `order_id` / `amount` → 明确冲突，不返回旧成功对象、不悄然执行新请求。
3. 不同主体利用返回的内部 key → 不得读取/复用他人的 Action；不得向模型/HTTP 泄露他人动作详情。
4. 并发重复请求 → 核查现有锁与 Store 是否保障单次执行；如果已安全，不改锁。

**修复范围**：先校验调用者与归属，再查/返回命中动作；外部幂等键与内部标识边界明确；请求指纹按 canonical action/user/order/amount 绑定并规范化金额。已有 owner 检查不能只在未命中路径生效。不要把真实外部支付 exactly-once 当目标。

**DoD**：专项修复前失败、修复后通过，跨用户敏感字段不出响应；相关 `tests/test_action_service.py` 回归通过；在 Workbench 的 A04 下面记录 `N01=fixed` 和限制。

## A04/N05（P1，N01/N02 稳定后）——动作成功被 Memory 失败遮蔽

**依据**：N05 / `ACTION_SUCCESS_MEMORY_FAILURE`；`api/main.py:399`。审查已观察取消订单成功且 Action completed，随后 `add_message` 失败使 HTTP 返回 500。

**红测设计**：Fake Agent 模拟成功动作、让**执行后的** Memory 写入失败；断言不把业务 Action 误标失败、不重复执行；响应包含正确的结果/可查询 receipt 或明确的恢复凭据及 Memory 降级状态。测试要区分**请求前 Memory 读取故障的 fail-closed**与**动作完成后写入失败**，不能为了掩盖后者把全部 Memory 变成 silent failure。

**修复范围**：最小调整执行回执/HTTP 返回与错误转换，允许先从可信 ActionStore 查询既有结果，限制敏感错误细节；不要引入全量后台任务队列或重写 Memory。

**DoD**：原动作只执行一次；即使响应/Memory 失败，用户能判断并查询真实业务状态；现有 Redis fail-closed 路径不回退；不将模拟 `completed` 描述为资金到账。

## A04/N04（P1）——模拟退款写后查询不一致

**依据**：N04 / `REFUND_READ_WRITE`；`actions/backend.py:56`、`providers/mock_backend.py:74`。Action `completed`，订单 `refund_pending`，但没有可供退款进度查询的 RefundRecord。

**红测设计**：模拟申请退款 → 审批/执行（按现有 Policy）→ 退款查询；断言可查到同 order/amount 的**pending** 记录，绝不虚构到账。重复动作不得生成重复记录。

**修复范围**：在现有演示业务后端维护读写一致的退款记录和状态映射；校验当前 API startup 与 isolated fixture 对读写共享的差异，不直接根据 isolated fixture 的结果推断生产路径。

**DoD**：退款写-查形成一致的演示状态链，原有取消/查询测试不回退。顺带修正 `providers/mock_backend.py` 与真实注册状态冲突的头部注释（若当前仍存在）。
