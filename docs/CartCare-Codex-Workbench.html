2. 项目目标与业务边界

核心用户

中小型电商平台的一线客服场景。用户通过对话查询政策、订单、物流、库存，发起售后，并在复杂或高风险情况下转人工。

CartCare 应做

FAQ/政策问答、商品咨询、订单/物流/库存查询、售后资格判断、退款/取消前置校验、人工升级、Trace 与 Eval。

CartCare 暂不做

完整商城、支付网关、真实客服工单平台、推荐系统、营销自动化、复杂 CRM。只实现足够支撑 Agent 工程能力的业务后端。

四类 Source of Truth

类型示例推荐来源不能怎么做
静态/半静态知识退货政策、配送规则、会员说明RAG / versioned docs不要从订单数据库“猜政策”
动态业务事实订单状态、物流、库存、退款状态Provider / Repository / API / DB不要用 RAG 回答实时状态
可执行动作申请退款、取消订单、创建人工工单Tool + Policy Gate + 幂等执行不要让 LLM 直接承诺执行成功
高风险决策超额退款、异常账户、投诉升级确定性规则 + HITL不要只靠 prompt 约束

4. P0–P3 改造路线

P0 建立真实业务闭环

收敛业务域；实现 mock business backend / Provider；新增 Order、Logistics、Inventory、Refund；实现 Refund/Cancel Policy Engine；HITL/approval/checkpoint；修复测试运行环境。

P1 可靠 Agent Runtime

统一 Tool schema/executor；风险分级、timeout/retry/idempotency；RAG metadata/citation/low-confidence；专项 Eval；durable trace 基线。

P2 简化与可观测

重新验证三路 Intent 和 Multi-Agent 是否必要；收缩长期 Memory；完善前端 Trace/引用/审批卡片；性能与成本指标。

P3 可选增强

标准 MCP、Hybrid Search、Reranker、Corrective/Self-RAG、真实外部电商 API、认证/多租户。只有当 P0–P2 指标证明需要时再做。

7. Codex 核验队列

每个任务完成后，不只问“代码写了吗”，而要让 Codex 回答：调用链真的接上了吗？测试能跑吗？失败路径是什么？README 是否同步？

每次提交前

检查 diff 是否只修改计划范围；运行相关 unit/integration tests；确认没有 Mock 冒充真实动作；检查 Tool/Policy/HITL 是否存在绕过路径。

每个阶段完成后

重新扫描主链路；更新 Current State Baseline；输出新增能力、未完成缺口、文档漂移、测试结果和回滚点。

当前协同原则：
1. 真实调用链 > README 描述。
2. 静态/半静态政策知识走 RAG；订单、物流、库存、退款状态走 Provider/API/DB。

5. 每次改动必须有可执行测试与可追踪证据；不要只让代码“看起来存在”。
6. 不默认保留 Multi-Agent。若单 Agent + Tools 更简单且指标不差，应优先简化。
