## N08：按会话串行化压缩

`memory/conversation_memory.py`：

- `add_message` 和 `add_message_once` 在同一个会话的 `asyncio.Lock` 内完成 LPUSH/原子脚本与压缩触发。
- `_compress` 拆成取锁入口和 `_compress_locked`；内部调用 `_compress_locked`，避免重复取锁死锁。
- 锁存放在 `WeakValueDictionary`，避免每会话锁无界增长。
- 单实例边界：锁只覆盖当前进程；多 worker 并发仍不承诺。

测试 `test_compression_never_drops_concurrent_messages`：

1. 预填 15 条消息，关闭自动压缩。
2. 启动 `_compress`，fake Redis 在 `ltrim` 前暂停。
3. 并发写入 6 条消息；断言它们必须等待压缩锁。
4. 释放后断言 6 条消息全部保留，列表长度 11。

修复前该测试失败：`ltrim 0..4` 只保留最新 5 条，6 条并发消息中最早的一条被丢弃且未进入摘要。

## N09：绑定触发消息 + 画像 RMW 串行化

`update_profile(user_id, conv_id, message=None)`：

- 有 `message` 时直接对触发消息调用 `explicit_preferences`，不再读取“最新用户消息”。
- 没有 `message` 时保留旧回退，兼容既有调用和 live 测试。
- `api/main.py` 调度后台任务时传入 `req.message`。
- 按用户 `asyncio.Lock` 锁住 `_get_profile` → merge → `upsert`，避免并发 read-modify-write 丢失不同字段。
- 语义仍是“最新显式指令覆盖同字段”，但不同字段不再因竞态互相覆盖。

测试：

- `test_profile_update_uses_triggering_message_not_latest_message`：后台任务暂停时写入新的英文偏好消息，最终仍记录触发消息的中文偏好。
- `test_profile_updates_serialize_read_modify_write`：第一个更新暂停时第二个必须阻塞在读之前；释放后 `reply_language=中文` 与 `reply_detail=详细` 同时保留。

## N11：超时不自动重试

`core/tool_contract.py` 的 `asyncio.TimeoutError` 分支改为立即返回：

- 同步 handler 的 worker 线程可能仍在运行；自动重试会与其重叠。
- `ToolExecutionResult.retryable` 仍为 True，模型仍可看到 `retry_later` 建议，但 `attempts=1`，不在本次调用内自动重放。
- 已完成的可重试失败（`dependency_failure` 等）行为不变。

测试：

- H3-1 集成测试从 `attempts=2` 改为 `attempts=1`，并断言 handler 只调用 1 次；修复前该断言失败。
- `test_sync_read_timeout_is_not_auto_retried` 直接覆盖同步 handler + `max_attempts=2`：timeout 后 `attempts=1`、worker 调用 1 次。
- 既有 `test_retryable_read_failure_retries_once` 仍通过，确认非超时失败仍可重试。

## N14：liveness / readiness 分离

`memory/conversation_memory.py`：

- `__init__` 保存 `self._chroma`。
- `readiness()` 执行 Redis `ping` 与 Chroma `heartbeat`，返回 `{"redis": bool, "chroma": bool}`；不调用模型，不回显异常文本。

`api/main.py`：

- `GET /health`：保持 liveness，只判断 orchestrator 已初始化。
- `GET /ready`：检查 orchestrator + Redis + Chroma；全部就绪返回 200：
  ```json
  {"status":"ready","checks":{"orchestrator":true,"redis":true,"chroma":true}}
  ```
  否则 503 `{"status":"not_ready","checks":...}`。

部署接线：

- `Dockerfile` 的 HEALTHCHECK 与 `docker-compose.yml` 的 app healthcheck 改为 `/ready`。
- nginx 的 healthcheck 仍走 `/health`（liveness）。
- 本次未重建应用镜像；容器内 `/ready` 留给 H5-1 干净环境验证。

测试：

- `/health` 不调用 readiness（fake memory 的 readiness 若被调用会暴露）。
- `/ready` 全就绪 200；Chroma 未就绪 503；无 Memory/orchestrator 503；响应不包含异常文本。
- `test_memory_readiness_checks_redis_and_chroma` 覆盖 Redis/Chroma 成功与失败。
- 真实 Redis/Chroma live 测试增加 `await memory.readiness() == {"redis": True, "chroma": True}`。

## 新发现的问题与限制

- 会话锁和画像锁是**进程内** `asyncio.Lock`；单实例可用，多 worker 仍不承诺。
- `/ready` 每次探测 Chroma heartbeat，可能比 `/health` 慢；只检查服务可用性，不检查知识库集合/文档完整性。
- 超时不自动重试后，模型需要显式再发起一次；这是避免 worker 重叠的有意取舍。
- 画像更新仍以最新显式偏好覆盖同字段；这是产品语义，不是并发丢失。
- Docker healthcheck 已改为 `/ready`，但本次未重建镜像；H5-1 需在干净环境确认容器健康状态。
- 未调用真实模型；N08/N09 的测试使用 fake Redis/Chroma，另有一条真实 Redis/Chroma live 回归。

| 事项 | 现状 | 建议 |

| 多 worker 下的 Memory 压缩/画像一致性 | 会话锁、画像锁都是进程内 `asyncio.Lock`；单实例有效 | 多 worker 需要 Redis 锁或单写队列，另开任务 |
| `/ready` 的检查深度 | 只探测 Redis ping 与 Chroma heartbeat，不检查知识库集合/文档完整性 | 需要区分“服务可用”和“知识库可检索”时再加轻量 collection 检查 |

| 超时后的模型重试 | 工具层不再自动重试；模型可能再次发起调用 | 结合 H3-1 循环/重复限制观察；真实模型评测时记录是否出现重复调用 |
| 慢 Chroma 对会话写入的影响 | 压缩/画像锁内包含 Chroma 调用；慢依赖会让同会话/同用户更新等待 | 作为延迟边界记录，不在 H4-3 做异步降级 |
| readiness 失败原因 | `/ready` 只返回布尔值，不泄露异常文本 | 运维需要诊断时加内部日志/指标，不把异常细节返回给客户端 |
