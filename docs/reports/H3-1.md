## 调用路径变化

- 之前：`BaseAgent._call_llm` 只有 `for _ in range(max_tool_rounds)`；超限 `raise RuntimeError`；Trace 无停止原因。
- 现在：同一循环内新增
  1. 每轮累计 `usage.input_tokens + output_tokens`；
  2. 每个 tool_use 执行前做“连续相同 `(tool, canonical args)`”检测；
  3. 再检查已执行步数；
  4. `execute_tool(..., timeout_s=harness.tool_timeout_s)`；
  5. 结束时写入 `StopReason`，返回回执或固定话术，不再抛异常。
- 生产 `/chat` 响应契约未改；`/trace/tool/{request_id}` 的 trace 多一个 `stop_reason` 字段。

## 默认值与数据依据

- **轮次上限保持 3**：H2-3 real2 与 H2-4 首轮共 **373 个真实 turn**，工具步数 p50=2、p95=3、max=4；只有 1 个 turn >3（0.27%）。3 轮覆盖 99.7%，同时能截断异常长链；不为了个别 4 步样本放宽。
- `max_tool_steps=8`：真实最大 4 步，留 2× 余量。
- `max_tokens_per_turn=60000`：真实每请求平均约 2.4k input，4 步约 10k，留足余量；假模型 usage=0 时不触发。
- `duplicate_call_limit=3`：同一 `(工具, 参数)` 连续第 3 次不再执行；写动作本身还有幂等键，重复执行不是唯一防线。
- `tool_timeout_s=30`：与现有只读工具默认一致，仅作为上限/缺省。

## 行为变化（必须在升级说明中单列）

1. 生产默认下，同一调用连续第 3 次、第 9 个工具步、或单轮 60k token 会**主动停止**；以前会继续到 3 轮上限。
2. 轮次耗尽不再抛 `RuntimeError`，而是返回既有 Action 回执；无回执时返回固定话术“本次处理已达到工具调用上限…”，`stop_reason=budget_exhausted`。
3. `loop_control=False` 时，轮次、步数、token、重复检测四项一起关闭（消融语义一致）；只保留 `unguarded_max_tool_rounds` 硬上限。
4. 两个既有测试显式把 `duplicate_call_limit` 调到 10，因为它们的脚本刻意重复同一调用；没有放宽任何断言，重复检测由 H3-1 新测试覆盖。

## 新发现的问题与限制

- **写动作没有执行超时**：只读工具受 `timeout_s` 约束；写动作被取消后 worker 可能继续运行，这是既有安全边界。`tool_timeout_s` 不能描述成对所有工具生效；N11 在 H4-3 复核。
  - **H4-3 后续变更**：N11 收口后，`execute_tool` 的 `TimeoutError` 分支立即返回，不再自动重试；`attempts=1`。本文“只读重试受 RetryPolicy 限制”仍适用于已完成的 retryable 失败，但不适用于超时。最新口径见 `docs/reports/H4-3.md`。
- **`needs_clarification` 是窄措辞启发式**：只写入 Trace，不改变回复或路由；例如政策文本里的“请提供订单号”可能被误判，报告不把它当作澄清率指标。
- **重复检测按原始参数比较**：`{"order_id": "ORD-1"}` 与多余空白/字段顺序不同的等价参数不会被归并；规范化参数属于 H3-2 的结构化错误/工具契约范围。
- **`max_tokens_per_turn` 未在真实模型下验证**：假模型 usage=0 不触发；真实触发效果留给 H3-6 消融。
- 停止原因没有进入 `/chat` 响应体，只看 admin Trace；如果演示需要展示，H5-3 再决定是否暴露。
