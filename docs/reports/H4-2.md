## 目标与结论

H4-1 留下两个崩溃窗口：`EXECUTING` 无法对账、Memory 回执与 `mark_resumed` 非原子。H4-2 在真实 Redis 上把进程杀死在审批前、审批中、执行中、执行后，再用新实例恢复并断言：

- 状态不伪装完成；
- executor 没有第二次执行；
- 动作/检查点回执可查询；
- Memory 回执最多写一次。

四个时间点都通过；执行中“已提交但无回执”按 `execution_unknown` 失败收口，这是有意的保守语义。

## 执行与恢复时序

```text
request_refund
  → Policy: require_approval
  → status=awaiting_approval, save
  → checkpoint saved (awaiting)

reviewer approve
  → status=approved, save
  → status=executing, save                 # 执行中窗口 A：已进入执行，未派发
  → execution_attempted_at=now, save       # 执行中窗口 B：已派发
  → executor.execute()
  → execution_result=receipt, save         # 执行中窗口 C：回执已落，状态未落
  → status=completed, save                 # 执行后窗口 D：动作完成

checkpoint resume
  → 逐 action 读取真实状态
  → approved / executing 调用 ActionService.resume
  → executing 恢复：
       有 execution_result      → completed（不重跑）
       无结果、未派发            → approved 后重跑一次
       无结果、已派发            → failed / execution_unknown（不重跑）
  → 终态生成逐动作回执
  → Memory.add_message_once(key=checkpoint_resume:<request_id>)
  → mark_resumed
```

`execution_attempted_at` 和 `execution_result` 都写在 action JSON 里，随 Redis ActionStore 持久化；没有新增存储。

## 杀进程场景与结果

`tests/test_h4_2_live_crash.py` 每个场景：

1. 用随机前缀启动 `python -m tests.h4_2_child`；
2. 子进程在目标点写 ready 文件后阻塞；
3. 父进程轮询到 ready 后 `Popen.kill()`（Windows TerminateProcess / POSIX SIGKILL）；
4. 父进程用全新 `RedisActionStore`/`ActionService`/`CheckpointService` 读回并恢复；
5. 通过 `TestClient` 调用 `GET /checkpoints/{request_id}` 与 `GET /actions/{action_id}` 验证回执。

| 场景 | 杀进程位置 | 重启后读回 | resume | 新进程 executor | Memory |
| --- | --- | --- | --- | --- | --- |
| 审批前 | 检查点已写、未审批 | `awaiting_approval` | reviewer 批准 + resume → completed | 1 | 1 |
| 审批中 | `approved` 已落、未派发 | `approved`；GET 投影为 executing | resume → completed | 1 | 1 |
| 执行中（已提交、无回执） | backend 已提交、executor 未返回 | `executing` + `execution_attempted_at`，无回执 | resume → failed / `execution_unknown` | 0 | 1 |
| 执行中（回执已落、状态未落） | `execution_result` 已保存、仍 `executing` | `executing` + 回执 | resume → completed（用回执） | 0 | 1 |
| 执行后（状态已落、未汇报） | `completed`、检查点未更新 | `completed`；GET 投影 completed | resume → completed | 0 | 1 |
| 执行后（Memory 已写、未标记） | `add_message_once` 已追加、未 `mark_resumed` | `completed`，Memory 1 条 | resume → completed，`already_written` | 0 | 1（不重复） |

补充：`test_memory_add_message_once_is_atomic_and_idempotent` 直接验证同一 idempotency key 第一次返回 `True`、第二次 `False`，列表长度保持 1。

## 关键语义

### `execution_unknown`

模拟业务表仍是进程内 fixture，重启后没有订单/退款记录可对账。动作已派发但未留下 `execution_result` 时，无法判断 backend 是否提交成功：

- 自动重放可能造成真实重复执行；
- 宣称 completed 会伪造结果；
- 因此置 `failed`，`error_code=execution_unknown`，消息明确“不能确认是否完成；未自动重试”。

`GET /actions/{id}` 和 `GET /checkpoints/{id}` 都能读到该终态；resume 仍会写一条失败回执到原会话。该动作使用原 idempotency key，同一请求重试会复用 failed 结果；需要人工核对或新请求。

### Memory 幂等

`add_message_once` 的 Lua 在同一个原子脚本里完成：

```text
marker 存在 → 返回 0
否则 LPUSH 消息 → EXPIRE 工作记忆 86400 → SET marker EX 86400 → 返回列表长度
```

marker 键：`wm:once:<quoted user>:<quoted conv>:<sha256(idempotency_key)[:32]>`。这样“Memory 已写、进程被杀、mark_resumed 未写”的重试不会重复追加；并发 resume 也只有一个请求真正追加。`delete_session` / `delete_user_memory` 同时清理该会话的 `wm:once:` marker，避免会话删除后旧 marker 抑制新回执。

### GET 对账

`GET /checkpoints/{request_id}` 用 `ActionService.get` 读取每个 action 的真实状态，返回 `reconcile_checkpoint` 的只读投影：

- 审批中崩溃时，存储仍是 awaiting，但响应显示 executing；
- 执行后崩溃时，存储仍是 awaiting，但响应显示 completed；
- 不在 GET 中写 Redis；resume 时才持久化动作状态。

## 新发现的问题与限制

- **执行中已提交但无回执无法对账**：模拟业务表不持久，只能保守收口为 `execution_unknown`；真实后端需要按 action_id 的幂等查询/补偿任务。
- **`execution_unknown` 动作不能自动重试**：原 idempotency key 会复用 failed 结果；需要人工核对或新请求。
- **单实例**：Redis `RLock` 不是分布式锁；多 worker 并发仍不在承诺内。
- **GET 对账是只读投影**：存储的检查点可能暂时落后，resume 才修复；GET 不写 Redis。
- **Memory marker TTL 24h**：与工作记忆一致；若手工删除会话列表但保留 marker，重试可能不补写。
- **未启动完整 uvicorn 重启**：恢复使用新 store/service 实例和 TestClient；进程 kill 本身是真实的，应用 lifespan 未参与。
- **孤立 idem 键**（H4-1 输入）仍未处理：action 键被删而 idem 键仍在时，`_request` 会在 Lua 绑定处抛未捕获异常；本次未扩大范围。
