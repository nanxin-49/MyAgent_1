## 调用路径变化

`BaseAgent._call_llm` 在原有工具循环内新增按步记录（不改变控制流）：

1. 每轮调用 `messages.create` 前创建 step 并立即写入 `self._last_steps`；`finally` 记录实测 `latency_ms`，异常时记录 `error_type`。
2. 从本次响应 `usage` 写 `input_tokens` / `output_tokens`（同时继续累计到原有 token 预算）。
3. 无 `tool_use` 时，把 `classify_answer` 的结果写入该 step 的 `stop_reason` 后返回。
4. 每个已执行或跳过的工具 trace 生成后，追加一份紧凑摘要到当前 step 的 `tools`；工具执行期间的 RAG SDK 调用只计为 `aux_model_calls`。
5. token 预算、重复调用、步数预算终止时，同步写当前 step 的 `stop_reason`；轮次上限退出时最后一步标 `budget_exhausted`。
6. `handle` 异常路径把最后一步标 `unrecoverable_error`；根节点 `stop_reason` 语义不变。

Trace 根节点新增：

```text
steps: [{step, model, input_tokens, output_tokens, latency_ms, tools, stop_reason}, ...]
step_count
step_scope
```

`step` 与 `context_rounds[].round` 对齐，可交叉查看每轮上下文构成。工具摘要字段：

```text
tool_name, risk_level, parameter_summary, result_summary,
success, error_code, error_type, retryable, latency_ms, attempts, aux_model_calls
```

`result_summary` 只含 `success`、`result_success`、`error_code`、`truncated`，并按存在性追加 `action_status`、`handoff_status`/`handoff_created`、`retrieval_status`、`citation_count`、`retrieval_hit_count`、`business_fields`。

## 新发现的问题与限制

- 一步 = 一次 Agent 模型调用；工具内部的 RAG 改写/重排 SDK 调用只在 `aux_model_calls` 计数，详情仍在根节点 `model_calls`。当前 `search_knowledge_base` 是 async handler，在事件循环内执行，因此能被计数；若将来把 RAG 调用放进不继承 ContextVar 的线程，计数会偏少。
- 确定性交接路径没有模型调用，因此 `steps=[]`；交接工具仍在 `tool_calls` 中，轨迹可复盘但不含模型步。
- 最终回复文本不写入 Trace（沿用既有隐私边界），只在 `/chat` 响应中；Trace 复盘的是执行轨迹，不是回答全文。
- 参数摘要来自已记录的工具 `input`，字符串截断到 120 字符、最多 12 个字段；完整参数仍在 `tool_calls[].input`。
- 旧 Multi/实验 Agent 路径不接入 `steps`；生产拓扑是 Single，无线上影响。
- Trace 仍是有界进程内队列（默认最近 200 个请求），重启丢失。H4-1 只持久化待审批动作和检查点，不包含 Trace；跨重启 Trace 需要在 H6-4 可观测平台（可选）中另行实现，目前未排期。
