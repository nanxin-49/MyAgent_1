## 调用路径变化

- `BaseAgent._call_llm` 每轮 `messages.create` 前：
  1. 用 `_build_system_prompt(req)` 和工具 schema 计算固定部分；
  2. `compose_context(messages, system, tool_schemas)` 得到六类构成；
  3. `context_compression=True` 且超 `max_context_tokens` → `compress_messages`；
  4. 追加一条 `context_rounds`（`round`、`estimated_tokens`、`compressed`、`over_budget`）。
- 压缩只改模型可见消息：旧 tool_result 保留 `success`/`error_code`/`suggested_action`/`retrieval_status` + 200 字符预览并标 `compressed`；背景消息截 400 字符；较早对话截 300 字符。**system prompt、工具 schema、当前用户消息永不压缩。**
- 关闭 `context_compression` 时只记录统计，不压缩；Trace 同样带 `context_rounds`。
- 生产默认预算 16000：实测 system ≈ 1048 token、15 个工具 schema ≈ 1437 token，正常请求不会触发压缩。

## 新发现的问题与限制

- token 是估算值，不能当计费或模型上下文上限的精确依据；Trace 字段名为 `estimated_tokens`。
- 压缩会丢失旧工具结果的细节；默认预算下正常请求不触发，低预算下的质量影响未测（H3-6）。
- 只压缩消息，不压缩 system prompt 和工具 schema；固定部分本身超预算时标 `over_budget`，不强行破坏。
- `context_compression` 现在同时控制 Memory 的 15 条压缩和 prompt 预算压缩；H2-1 报告中“评测工厂无可观察效果”的限制在本任务后已不再成立（历史报告保留不改）。
- 压缩后的 tool_result 仍保留 H3-2 的结构字段，但长 `retrieval` 内容只剩预览，引用/证据仍以 Trace 中的完整字段为准。
