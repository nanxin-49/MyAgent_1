## Redis 设计

### ActionStore

- 键：`<prefix>:action:<action_id>` -> `PendingAction.model_dump_json()`；`<prefix>:idem:<idempotency_key>` -> action_id。
- `save` 用 Lua 原子脚本：如果 idempotency key 已绑定其他 action_id，返回冲突（`IdempotencyConflict`）；否则同时写 action 与 idem 映射。避免两个 action 共用一个 key。
- `get` / `find_by_idempotency` 读取并 `PendingAction.model_validate_json`；损坏数据 fail closed。
- `lock = RLock()`，`ActionService` 继续用进程内锁串行化；**不是分布式锁**。
- 无 TTL；prefix 由 `CARTCARE_ACTION_PREFIX` 覆盖，默认 `cartcare:actions`。
- 构造时 `ping()`；Redis 不可用则应用启动失败，不静默回退内存。

### CheckpointStore

- 键：`<prefix>:checkpoint:<request_id>` -> `ActionCheckpoint` JSON；`<prefix>:action:<action_id>` -> request_id。
- 每次 `save` 用 Redis transaction pipeline 同时写检查点和 action 索引。
- prefix `CARTCARE_CHECKPOINT_PREFIX`，默认 `cartcare:checkpoints`；无 TTL。

## 检查点字段

```text
ActionCheckpoint:
  request_id, conv_id, user_id
  actions: [{action_id, tool_name, status, error_code}]
  steps: H3-5 的安全摘要（step/token/工具/参数/结果/停止原因）
  status: awaiting_approval | executing | completed | partial_completed | rejected | failed
  remaining_actions: 非终态 action IDs
  created_at, updated_at, resumed_at
```

- 只在 `/chat` 观察到至少一个 `awaiting_approval` 时创建；completed-only 不创建。
- 不保存 prompt、模型文本、隐藏推理、原始 Memory 内容。
- `remaining_actions` 是动作诉求的确定性代理；**没有 Planner/读类诉求状态**，报告明确边界。

## API 与恢复流程

- `/chat` 在 `runtime.run` 后调用 `CheckpointService.record_result`；检查点写入失败只记 `warning_codes`/日志，不把已完成的 action 响应变成 500。
- `approve` / `reject` / `resume` 在动作成功返回后更新检查点；更新失败只记日志，不回滚动作。
- `GET /checkpoints/{request_id}`：owner-only；不存在/非 owner 404。
- `POST /checkpoints/{request_id}/resume`：owner-only。
  - 对每个 action 调 `ActionService.get` 重新校验 owner；`APPROVED` 调 `ActionService.resume` 执行；`AWAITING_APPROVAL` 不执行；`EXECUTING` 只报告状态（崩溃窗口留给 H4-2）。
  - 仍有 awaiting：返回 `awaiting_approval`，不写 Memory。
  - 全部终态：生成逐动作回执，追加到原会话 `MemoryManager.add_message(MsgRole.ASSISTANT, ...)`，标记 `resumed_at`。
  - 已 resumed：返回同一回执，`already_resumed=true`，不重复写 Memory。
  - Memory 写失败：返回 `memory_write_status=failed`，不标记 resumed，可重试。
- 身份只来自服务端 Principal；审批仍要求独立 reviewer，检查点不绕过审批。

## 真实 Redis 证据

`tests/test_h4_1_live_persistence.py`（`CARTCARE_TEST_LIVE_ACTIONS=1` + `REDIS_URL`）包含两个场景：

### 新实例读回与恢复

1. 服务 A 用 `RedisActionStore`/`RedisCheckpointStore`；`ORD-H23-APPROVAL-1` 退款 800 -> `awaiting_approval`；写检查点；关闭 A 的 store。
2. 服务 B 用新 store/client 读回同一 pending action 和检查点；`get` 仍为 `awaiting_approval`。
3. reviewer 通过 HTTP 批准 -> `completed`；B 的 executor 调用 1 次。
4. `GET /checkpoints` 显示 `completed`；`POST /checkpoints/{id}/resume` 返回 `completed` 回执，Memory 写入 1 次；再次 resume 为 `already_resumed`，不重复写。
5. 同订单/金额/用户在 B 上再次请求 -> `reused=true`，executor 仍 1 次，证明 idempotency 绑定跨实例。
6. 其他客户读取/恢复 -> 404。

### 真实子进程重启

同一 live 测试文件里的第二个场景用两个独立 `python -c` 子进程：

1. 子进程 1：写入 pending action + checkpoint，输出 action_id/request_id 后退出。
2. 子进程 2：全新 Python 进程、全新 Redis store/Service，读回 `awaiting_approval`，reviewer 批准 -> `completed`，检查点同步为 `completed`。
3. 父测试断言 `before=awaiting_approval`、`approved=completed`、`checkpoint=completed`。

这覆盖了**真实 OS 进程重启**后的待审批动作读取与批准；四个时间点的杀进程/执行中窗口由 H4-2 验证。

## 新发现的问题与限制

- **单实例**：Redis `RLock` 只在进程内；多 worker 并发不承诺，需要分布式锁/队列是后续工作。
- **模拟业务表仍内存**：重启后审批能执行，但业务表从 fixture 重建；H4-1 只承诺 action/checkpoint 持久化，不承诺业务数据持久化。
- **EXECUTING 崩溃窗口**：H4-1 对 `EXECUTING` 只报告状态，不重新执行；H4-2 会杀进程验证四个时间点。
- **检查点只覆盖动作诉求**：读类/FAQ 诉求没有 Planner/子任务状态；`remaining_actions` 只是动作 ID 代理。
- **无 TTL**：动作/检查点不会自动过期；需要清理策略时另议。
- **Redis 启动依赖**：Redis 不可用时应用启动失败（与 Memory 一致），不静默回退内存。
- **未知恢复**：如果检查点/动作数据损坏或 action store 中丢失 action，resume 返回 failed/404；不编造状态。
- **Memory 写失败**：返回 `memory_write_status=failed`，检查点保留可重试；但若 Memory 写成功、检查点标记失败，可能重复写一次（单实例窗口小，未处理）。
