# A02 / C04｜结构化 Handoff：不能把“拒绝服务”一律判作转人工

**证据**：报告 C01/C04/C09；`agents/agent_orchestrator.py:478` 的 `_needs_escalation` 使用关键词，可能对“不需要人工客服”误触发；`create_handoff_summary` 只生成摘要，未建单。T10 unsupported 案例的 `0/3` 是**与旧 rubric 不匹配**，不能单凭它认定“拒绝订票不合理”。

## 业务语义先定清

| 场景 | 期望处理 | 不得伪称 |
| --- | --- | --- |
| 用户明确要求人工 | 申请结构化演示交接 | 单说“转人工”就算已建单 |
| “不需要人工客服” | 不建工单 | 文本包含“人工”就触发 |
| 非本平台能力（例如订票） | 明确业务范围、说明无法办理；**按升级政策决定是否提供人工选项** | 所有越界请求自动建单 |
| 缺订单号/必要参数 | 先追问所需信息 | 一律升级 |
| 合规/依赖故障且确实需人工 | 尝试创建工单，返回结果 | 失败仍声称人工已接单 |

## 实施与测试

`Agent/确定性路由 → request_handoff → 最小 Demo HandoffService → handoff_id + status(created|failed) → /chat + Trace`。根据既有架构最小实现，不接第三方工单/SLA、坐席系统。新建工单与模型建议分开；`required`、`requested`、`created`、`failed` 为明确不同状态。

先写至少五个案例：明确人工、否定人工、越界合理拒绝、业务服务失败、普通 FAQ/订单查询；覆盖 HandoffService 成功和失败、模型在结尾失败的回执真实性。对 unsupported 的评测**同时重审旧 rubric**（“合理拒绝”与“应该升级”两种 gold），新 rubric 要独立版本，不重写 T10 历史数据。

## DoD

API/Trace 中的 `handoff_id` 与状态来自真实 Demo 服务返回；无事件时不能因回答关键词标记创建成功；未创建不能称“已有人承接”；增加最小服务层测试及一个 `/chat` 路径用例；记录不支持场景的确定性理由码/规则，而非恢复 IntentRecognizer 或多 Agent。
