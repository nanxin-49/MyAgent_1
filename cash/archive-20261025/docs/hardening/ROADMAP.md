## 1. 项目定位与能力判断

建议定位：**有证据约束、受控动作和可复现评测的电商客服 Agent 原型**。面向订单、物流、商品、库存、政策问答及有限售后，业务后端明确为模拟系统。

| 维度 | 当前能证明什么 | 还不能据此证明什么 |
| --- | --- | --- |
| Agent 架构 | 实际 `/chat` 使用 SingleSupportAgent + Tool Contract；有最大轮次、白名单及逐请求 Agent 状态 | 复杂任意任务规划、所有复合请求均完成 |
| 业务建模 | Provider 提供动态事实，PolicyEngine 决定硬约束，ActionService 管理审批与执行 | 已接入真实商城、支付或客服坐席 |
| 安全控制 | 服务端 Principal、ownership、独立 reviewer、管理/Trace 授权与幂等回归 | Demo Auth 是生产认证，或公网部署已经安全 |
| RAG 工程 | 外部 Chroma HTTP、发布/退役生命周期、引用绑定、重排状态和冻结评测 | 语义检索已完成，或带引用的答案必然充分正确 |
| 故障处理 | 观察到缺陷后建立安全红测、最小修复；区分动作完成与 Memory 写入失败 | 跨进程 exactly-once、重启恢复、外部执行结果自动对账 |
| 可观测与评测 | 工具/动作/检索 Trace、隔离业务评测、失败样本和成本账本 | 进程内 Trace 等于持久审计；小样本通过率等于生产 SLA |
| 个人工程能力 | 有适合深入讲解的真实问题与取舍 | 仓库由 Codex 完成就等于本人能设计、调试和维护 |

因此可以写入简历；现在最有说服力的内容是“如何保证 Agent 不越权、不把文本当执行结果，以及如何用证据定位失败”。RAG 质量优化和稳定真实业务闭环应在补齐证据后再写成成果。本文不推断招聘市场录用概率，也不按框架数量打分。

## 3. 交付范围与完成定义

### 3.1 主线：受控本地电商客服原型

范围固定为单电商域、有限工具、受控本地演示和明确的模拟业务后端。保留政策问答、本人订单/物流、缺参澄清、模拟售后、审批/拒绝、状态查询、人工交接与故障说明。不得宣传真实支付、真人接单、公网生产认证、跨进程 exactly-once 或多 worker 可靠性。

主线完成须同时满足：

- **功能确实发生**：代表性政策问题实际走 RAG；模拟退款申请、必要审核、执行回执与状态查询形成闭环；订单/物流在跨轮状态改变后刷新 Provider。
- **回答与证据相符**：有效引用不是逐句事实认证；动态事实不能靠历史猜测；未知、部分可答与依赖失败分开。不能以全拒答代替产品可用性。
- **动作受控**：身份、归属、Policy、独立 reviewer 和幂等仍由代码控制；资格咨询不触发申请；模拟执行不等于到账；状态追问不新建交接。
- **默认路径无已知阻断缺陷**：越权、未授权写入、审批绕过和影响当前功能的状态丢失必须修复或切实消除可达路径。关闭功能须有配置、测试和明确范围说明，不是仅写“延期”。
- **可交付且可讲解**：指定版本可干净检出、测试和启动；本人能画主链路、改一个工具、写边界测试，并解释三个真实工程取舍。

取消订单若作为对外演示能力，应有独立真实闭环样本；未完成时明确该项仅有何种集成证据，不借退款通过冒充取消通过。仍暴露的写工具必须保留安全回归，不能靠“不演示”绕过已知安全缺陷。

### 3.2 主线验收与实验完成分开记录

**完整签署旧 26 题 Gold，不是少量自然用户 `/chat` 诊断的前置条件。** 每次新运行只需事先明确本批场景、必要事实、允许副作用、预期终态与判定规则；历史 Gold 的未批准状态照实保留。

B1 未运行，检索对照仍为 partial/blocked 或经用户确认的 deferred，不能标 `experiment_complete`。主线达到第 3.1 节范围时，可以独立验收交付版本；不再因 B1 未完成阻挡 Demo。

这两项结论在同一 Workbench/progress 的既有任务或备注中分别记录，不新增平行状态系统。若原 A05 定义包含实验，则保留其实验 partial；只有用户明确批准调整任务验收范围后，才能相应更新整体状态。文档修订不代替该确认。

### G1：优先补齐真正缺失的业务闭环

先做少量诊断，再按结果单问题修复。表中是覆盖维度，不要求新建 12 类×多轮的庞大前置数据集；已验证的非变更路径复用相应层级证据。

| 场景 | 本轮应观察的结果 |
| --- | --- |
| 有依据的政策问答 | 自然提问实际选择 RAG，获得当前证据并正确回答；直接背 Skill 不算 RAG 闭环 |
| 相近主题但缺事实 | 不编造到账、渠道、费用；有依据的边界解释与纯知识不足分开 |
| 本人订单/物流及状态变化 | 实际 Provider 查询；两轮间改变隔离状态，追问取得新状态，不靠历史碰巧答对 |
| 资格咨询与缺参 | 只说明/澄清，不默认申请，不猜参数 |
| 模拟退款申请与查询 | 明确申请 → Policy → Action → 业务状态查询；action completed 与 refund pending、真实到账区分 |
| 审核及拒绝 | 分别验证独立 reviewer 批准、客户拒绝自己的待审批请求、Policy 拒绝；审批前执行为 0 |
| 重复请求与异参冲突 | 同主体、同键、同参数按契约复用；异参/跨身份不能错取旧结果，执行计数可查 |
| 取消订单（对外展示时） | 独立验证其允许/拒绝状态与查询，不复用退款结果冒充 |
| 人工请求与历史追问 | 明确新请求才创建；历史/状态询问不新增；模拟回执不等于真人接单 |
| 无权限与敏感接口 | 真实 Principal 决定权限；模型拒绝与直接 gate 攻击测试分开，不能只凭模型未尝试就认定 gate 已验收 |
| 无答案、失效知识与依赖故障 | 知识不足、版本排除、RAG/Provider 失败分开；先复用隔离契约测试，按风险补少量真实链路 |
| 部分完成和后续故障 | 已完成动作有可查询回执；未完成部分不被宣称完成；不以 HTTP 200 计整体成功 |

审批语义以当前代码为准：`approve` 是独立 reviewer；现有 `reject` 是所属客户拒绝待审批动作；策略拒绝另列。**本计划不新增“reviewer 驳回”能力。** >500 元退款用独立、总额足够且状态/创建时间合法的 fixture，不能拿 129.90 元订单申请 600 元来测试正常审核链。

RAG 分两种证据：无模型的真实工具直调用于排除工具层故障；自然 `/chat` 用于验证模型选择和回答。明确要求“根据知识库回答”的诊断可补充，但不得替代自然工具选择成绩，也不能把工具名/Gold 偷放进用户不可见提示词。

失败按 `输入/预期 → 工具选择 → 参数/身份 → 结果/检索 → 生成 → 后处理 → API/业务终态` 归因。不得同时修改 Prompt、阈值、知识和判分规则。旧失败不删除；修复在新运行中验证。

### G2：主线回答验收与可选检索实验分开

主线只核对真实样本：必要事实是否有依据，否定/范围是否保留，动态状态是否刷新，partial/no_answer/degraded 是否正确说明。沿用已批准六篇正文和 0.35；本计划不授权调阈值或重写知识。若当前 RAG 在核心场景不可用，必须定向修复或经确认收窄对外范围，不能因为 B1 可选就放弃质量门。

旧 30 题用于原语料连续对照；26 题保留为 Answerability 契约材料及未完成审批记录。publishing 等技术问题不冒充用户流量分布。新自然场景另记身份、知识版本和预期，不建立“整体准确率提升”混合曲线。

只有另行授权 B1 时，才执行既定模型/revision、独立 collection、相同 corpus/Gold、dev 独立阈值校准及成本/延迟对照。测试结果不用于反复调参；标题等输入处理变化明确记作配置差异。B2 和新 holdout 以明确的失败归因或泛化目标为前提。

B0/B1 完整同口径运行才可写 `experiment_complete`；是否推广是另一决定，须有回退方案和真实 `/chat` 验证。没做 B1 不影响主线按第 3 节独立验收，但不得宣传已完成语义检索优化。

### G3：只补当前默认路径需要的边界

- **N08/N09**：保留压缩/画像则用受控 interleaving 及相关真实服务验证处理消息丢失、触发内容错绑；画像 RMW 线索另行复现后定性。暂缓时通过明确开关实际关闭，验证有界会话上下文、TTL 和隔离仍可用，不把静默丢消息当作降级。
- **C03**：定向验证末轮只读工具、多诉求部分完成及回执；符合预期则 verified_no_fix。复杂多动作规划不在首版承诺内，不引入新 Planner。
- **N11/C07**：验证默认读重试、预算和超时后 worker；不能把超时返回当成线程已取消。确有资源放大则用最小有界控制处理，不以扩大超时掩盖；不改写工具为可安全自动重试。
- **N14**：确保文档/入口不把进程存活当依赖就绪；需要时最小区分 readiness 与降级。健康探针不调用模型，不搭建新监控平台。

每项按实际风险确定是否进入本次交付；关闭能力也须经授权、测试和范围记录。单进程不自动等于无异步竞态，进程锁不推广为跨 worker 保证。

### G4–G5：固定候选并停止功能扩张

G4 在稳定后才固定一批正式验收场景，不先扩建大数据集。使用包含全部拟交付修复的提交或明确 patch/hash；本机离线通过、干净检出通过、远端 CI 通过分别记录。提交/推送仍需用户授权；未完成远端复验不能写“CI 已修复通过”。

交付复用 README、Workbench/progress、两份核心 Wiki 和一个证据索引；只同步实际漂移，不重写全站文档。启动说明列依赖版本、认证、知识状态、隔离数据、运行与清理命令和限制；Demo 覆盖能答、不能答、需审核、状态查询及重复请求。

G5 从本轮起穿插：画主链路、手写有界 tool loop、加 ownership/幂等回归、复现一个故障，并讲清 Single、确定性业务规则、RAG 与动态事实的分工。最后准备 5–8 分钟演示与三个工程故事；Codex 只能事后核对，不能代做并宣布掌握。

## 5. 两层验收与证据格式

### 5.1 诊断运行不等于正式验收

**诊断层**：复用现有自然问题和失败文本，通常每批 3–5 个相关场景，事先写明身份、预期事实与副作用。用途是定位问题，不宣传总体成功率；无需完整签署旧 26 题或新增通用评分器。

**候选验收层**：在运行前固定版本、核心必过任务、其余展示场景、必要分支、模型/fixture/预算和判定标准。可从约 10–12 个自然业务场景及必要分支起步，按能力覆盖而不是凑题数；若范围更小必须显式说明。关键路径做少量预先约定的独立重复，不默认要求全部 30 题和 ≥10×3 次真实调用。

| 验收维度 | 主线要求 | 必须保留的口径 |
| --- | --- | --- |
| 确定性安全回归 | 相关必需测试通过，关键 live 跳过另验或如实 blocked | 单元/服务/模型证据不混用 |
| 安全不变量 | 本次正式范围内不得有未处理的越权、未授权写入、审批绕过 | 给实际分母；零观测不等于绝对保证；直接 gate 测试另报 |
| 核心任务 | 预先指定的必过闭环全部有成功与终态证据 | 其他任务 pass/partial/fail 全量报告，partial 不计 pass；合理拒答与漏证据区别 |
| 关键重复性 | 对审批、幂等、追问写门等选定路径记录独立 trial | 次数与重置规则运行前确定；预算不足如实未完成，不挑最好一次 |
| RAG/回答 | 代表性主线真实使用知识；关键金额、资格、时效、动作事实有依据 | 来源有效不等于支持事实；safe refusal 不等于已知问题已完成 |
| 延迟与成本 | 记录 HTTP/runtime 耗时、调用、token、费用估算与超限行为 | 包含全部调用层和重试；小样本不过度解释 P95；估算与账单分开 |
| 复现 | 干净检出、锁依赖、基础 CI、指定启动路径可验证 | 历史本机通过不冒充当前远端通过 |

原计划“≥30 任务且 ≥90%、≥10 个关键任务各 3 次、RAG 80%/10%/95%、新 ≥40 题 holdout”不再作为首版统一必走门槛，转为需要该声明时另行批准的增强验收目标。**这是未来范围调整，不改写过去已锁定实验的门槛、评分或结论。**

正式运行后不能通过删失败、改分母、降低门槛或重命名 partial 来通过。发现缺陷修复后可形成新候选和新验收轮，保留前后关系。主线验收须同时看可用性与安全，不能用全部拒答刷分。

### 5.2 保留证据分层，减少无效文书

1. **unit / Fake SDK**：确定性代码与模拟序列。
2. **离线真实输出重放**：固定历史模型文本在当前后处理中的行为。
3. **live service**：真实隔离 Redis/Chroma，不代表模型理解正确。
4. **real model**：真实模型调用，未经过 API 就不叫 HTTP E2E。
5. **real-model HTTP E2E + 模拟业务**：当前 `/chat`、真实模型/依赖、隔离 Provider/ActionBackend。
6. **真实业务集成**：外部系统自己的终态证据；当前项目没有该层。

新运行沿用 `evaluation/reports/hardening/<Axx>/<run-id>/`。复用已有 REPORT、manifest、原文/工具结果、业务状态差异、判分与账本；一份文件能表达清楚就不重复生成多个审批包。manifest 绑定实际源码/patch、依赖锁、数据/知识、模型参数、时钟和预算；禁止覆盖原失败或保存密钥/隐藏思维链。

## 6. Codex 执行规则

1. 每轮一个有界 `Axx/issue-id`，不是执行所有 G 阶段的授权。读取 AGENTS、Workbench/progress、V3 README 和当轮小节；历史材料按需读取，不全面重审。
2. 保留起始 dirty 差异，先核对当前实现和证据。已修问题不重复造改动；缺陷先红测再最小修复，一次不混改多项实验变量。
3. 不重新建设评测平台、独立进度系统或全面 Gold 审批流；每份新增材料须直接服务当前定位、验收或复现。
4. 模型、网络下载、服务启动和外部写入按明确范围授权。旧额度不能自动变成新许可；同一授权的账本累计不重置；已授权的普通可逆步骤不反复要求确认。
5. 共享预算覆盖 Support、rewrite、rerank、Memory/profile 及 SDK/HTTP 重试。不能约束或核算时如实停止在调用前；不宣称账户级硬上限。
6. 安全违规、状态污染、预算超限或证据完整性异常时停止扩大运行并保留现场；修复另立 issue，不边跑正式集边刷通过。
7. 无可信原始资产时不重写历史 hash；内容改动用新版本及说明。不得用换行处理掩盖实质差异，不批量 renormalize 冻结材料来冒充恢复。
8. 实施完成建议 verify，用户决定 done。主线可独立交付，实验未完仍如实 partial/blocked/deferred；Codex 不代签批准。
9. 无相关生产变化且证据版本一致可引用已有回归，不重复刷全量次数；公共基础设施或调用链改变时运行对应回归及必要全量测试。
10. 结束只报告变更、实测、验收对照、限制、建议状态和一个独立练习；不自动 commit/push/merge、改生产数据或启动下一 issue。

## 8. 简历与面试交付口径

定位不变：**电商客服 Agent 与受控售后原型**，重点是 Single/Tools、确定性业务控制、知识与动态事实分离、真实故障定位，而不是框架数量或“企业级可靠性”。

当前描述可沿用：

> 开发电商客服 Agent 原型，采用 Single Agent + 工具架构，将实时业务查询、知识检索和售后动作分层；通过服务端身份、订单归属、确定性策略、独立审批与幂等控制约束敏感操作，并基于真实失败样本建立回归测试与可追溯评测。业务执行使用模拟后端。

主线验收后，简历压缩为四项成果：
- 架构取舍：为什么采用 Single，工具参数、风险和轮次如何控制。
- 受控动作：申请—审核—执行—查询，订单归属、独立审核和同主体参数绑定幂等。
- 知识证据：Chroma HTTP 发布/退役及引用hash；动态事实来自Provider，引用不冒充逐句事实认证。
- 真实诊断与交付：工具Trace、状态差异、历史文本回放、自然HTTP场景及可复现Demo。

上一轮仓库审阅核对了[T10历史报告](../../evaluation/reports/t10_topology_comparison.md)：10类场景×3轮/拓扑，两组任务成功均24/30，SDK调用由Multi的115降至Single的76（约减少33.9%），平均runner耗时6633.3→3937.1ms（约降低40.6%）。可以用于说明架构选择，但必须注明历史受控chat-style实验、模拟业务、不是当前生产POST /chat性能，也不证明Single普遍优于Multi。

新的量化成果仅用最终实际数据：“N个预定义任务、M次真实HTTP trial，在指定模型和模拟业务环境下严格成功P/M，观察到的安全违规V/M，延迟与费用为……”。不预填目标，不把测试数量当业务场景，不把零观测写成绝对保证，不把自研mcp目录写成标准MCP接入。

三个工程故事优先选：N01身份/幂等顺序，N05动作成功后Memory失败，真实交接误触发/REPLY误删。每个讲问题、根因、取舍、修复、证据和限制；本人必须能独立定位代码，不只是复述Codex报告。

## 执行结果的标准

- `fixed`：专项安全行为测试先红后绿；原用例回归无退化。
- `verified_no_fix`：当前工作区已符合预期，必须有实测证据；不可宣称旧问题从未存在。
- `implemented`：如 A02，有 API/Service + Trace 的业务闭环测试。
- `experiment_complete`：如 A05，有冻结数据、B0/B1 完整运行信息和逐题分析。
- `partial`、`deferred/known_open`：有清晰的未完成范围和原因。不把 15 条审查观察“断言通过”当 15 个漏洞“修复通过”。
